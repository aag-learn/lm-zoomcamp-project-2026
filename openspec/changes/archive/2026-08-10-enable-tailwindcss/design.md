## Context

The chat UI (`app/views/chats/`, `app/views/messages/`) was generated by RubyLLM's `chat_ui` scaffold generator and hand-extended with a `_feedback.html.erb` partial in `chat-interface-scaffolding` — all of it styled with inline `style="..."` attributes, no CSS framework. The `web` image's `Dockerfile` already runs `bin/rails assets:precompile` (added in that same change, to fix a missing-assets bug) — this matters because whatever Tailwind setup is chosen needs to fit into that existing build step without requiring a new toolchain in the image.

## Goals / Non-Goals

**Goals:**
- Tailwind CSS available and actually used across the chat-facing views, replacing inline styles.
- No new system-level toolchain dependency (this project has no Node.js/`package.json` anywhere — `importmap-rails` handles JS with zero build step).

**Non-Goals:**
- ~~Restyling `app/views/models/*.erb`~~ — **reversed**, see Decisions: the nav bar made the unstyled leftover in-page nav link a real, reported usability defect, not just inconsistent polish.
- A custom design system, component library, or dark mode — plain Tailwind utility classes applied directly, matching the scope of a styling pass, not a redesign.
- Changing chat/message behavior — presentation-only for those views. (The `default_model` change is a deliberate, small exception — see Decisions.)

## Decisions

**`tailwindcss-rails`, not `cssbundling-rails` + a Node-based Tailwind CLI.** `tailwindcss-rails` ships a standalone platform-specific Tailwind CLI binary (via the `tailwindcss-ruby` gem), resolved at `bundle install` time — no Node.js, no `package.json`, no separate JS package manager. This project already has zero Node.js footprint (`importmap-rails` for JS). Adding a Node-based build pipeline just for CSS would be a real new toolchain dependency for a single framework; `tailwindcss-rails` avoids that entirely and is the official Rails-maintained option (this is also what `rails new --css=tailwind` — mentioned in `PLAN.md`'s original setup notes — actually installs under the hood).

**Restyle only the chat-facing views** (`chats/`, `messages/`, `_feedback.html.erb`), not `models/`. The `models/` views are RubyLLM's auto-generated model-browsing/admin page, not part of the actual chat experience or anything the course rubric's Interface category evaluates. Restyling it would be scope creep for no rubric benefit; can be done later if it's ever actually used.

**Reversed above, once the nav bar made it a real problem, not just inconsistent polish.** `models/index.html.erb`'s in-page `<%= link_to "Chats", chats_path %>`, sitting right at the top of the page, now visually reads as a second broken nav directly under the real one — reported directly as "a weird menu inside the page." That's a genuine usability defect the nav bar itself introduced, not pre-existing scope creep — removed the redundant link and gave `models/*.erb` the same Tailwind pass as everything else (including the previously-unstyled "Refresh Models" button).

**`config.default_model = "gpt-5-mini"`, the `provider: "openai"` entry specifically.** `RubyLLM.models` has more than one `gpt-5-mini`-named entry — the one wanted is the direct OpenAI-provider one; the registry also has an OpenRouter-routed `openai/gpt-5-mini` (different `id`, `provider: "openrouter"`) which would silently fail or misroute since only `openai_api_key` is configured. Confirmed the exact ID via `RubyLLM.models.chat_models.select { |m| m.provider == "openai" && ... }` against the real loaded registry, not assumed from the model name alone.

**Flash messages consolidated into the layout, not fixed per-view.** The bug (`<main>`'s `flex` row layout + each view's flash `<p>` sitting as a sibling of, not inside, that page's centered content wrapper) existed identically in `chats/index.html.erb`, `chats/show.html.erb`, and `models/index.html.erb` — three copies of the same latent defect. Fixing it in three places would leave the duplication (and the risk of a fourth copy reintroducing the bug in some future view) in place; fixing it once in the shared layout removes both the bug and the duplication. `<main>` gets `flex-col` added — required, not cosmetic: once the layout also renders a flash message, `<main>` has two children (flash + yielded content) whenever a flash is present, and without `flex-col` the exact same side-by-side bug would recur one level up.

**Verify the Dockerfile's existing `assets:precompile` step picks up Tailwind's build automatically, rather than assuming.** `tailwindcss-rails` is documented to hook a `tailwindcss:build` task dependency onto `assets:precompile` — but per this project's established practice (`CLAUDE.md`), confirm this directly against the actual installed gem version and a real build, rather than trust the general claim. If it doesn't hook in automatically for some reason, the Dockerfile needs an explicit `tailwindcss:build` step added alongside `assets:precompile`.

**Persistent nav bar added to the shared layout (`app/views/layouts/application.html.erb`), fixed to the top of the viewport.** Confirmed the `<main class="container mx-auto mt-28 px-5 flex">` wrapper `tailwindcss:install` inserted already carries a large top margin (`mt-28`, ~7rem) — clearly anticipating a fixed-position nav bar that was never actually built, so a `fixed inset-x-0 top-0` nav matches spacing already in place rather than requiring new adjustments. Three links — Chats, Models, New chat — cover every section reachable today; current-section highlighting via a small `nav_link_active?(path)` helper in `ApplicationHelper` (checks `request.path.start_with?(path)`, broader than Rails' own `current_page?` so `/chats/:id` and `/chats/new` both count as the "Chats" section being active, not just the literal `/chats` index).

## Risks / Trade-offs

- **`bin/rails tailwindcss:install`'s generator output isn't yet inspected** — file names/exact structure confirmed empirically during implementation (first task), not assumed here, matching how `ruby_llm:install`/`chat_ui`'s actual output was verified rather than guessed in the previous change.
- **Restyling many small partials by hand is mechanical, easy to get visually inconsistent.** → Acceptable; a single pass applying a small, consistent set of utility patterns (spacing, borders, colors) across all the touched files, verified visually in a browser at the end, not per-file.
- **The new nav bar sits above `models/*.erb`'s still-unstyled content** (out of scope, per this design's own Non-Goals). → Accepted, explicitly — a known, visible inconsistency between a styled nav and unstyled page body, not fixed here; revisit only if `models/` restyling is separately requested.
