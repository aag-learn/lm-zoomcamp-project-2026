## Context

See proposal.md for motivation; see `PLAN.md`'s "Evaluation" section (revised 2026-08-18) for the full "why" behind the 6-module scope, the pinning decision, and the module-swap policy — this design only covers implementation shape, not those decisions.

Nothing in `lib/tasks/` exists yet beyond a `.keep` file — this is a greenfield rake-task area. Services this reuses without modification: `Retrieval::KeywordSearch`/`VectorSearch`/`HybridSearch`, `RerankerClient`, `SearchAnsibleDocs`/`GetModuleDetails` (the same `RubyLLM::Tool` subclasses `ChatResponseJob` registers), and `Chunk`/`AnsibleModule` (which already expose `stable_id`, `chunk_type`, and `raw_doc`). RubyLLM is already the app's structured-output-capable chat client (used for the live chat's completions); this change is the first place structured-output judging/generation gets used outside the live chat path, but through the same gem, not a second LLM client.

## Goals / Non-Goals

**Goals:**
- One rake namespace (`eval.rake`) with independently runnable tasks for ground-truth generation, retrieval eval, LLM eval, and compositional eval, plus a chained `eval:all`.
- Ground truth and results persisted as plain files the app can read without a DB round-trip.
- Every eval task exercises the exact same retrieval/tool-calling code the live app uses — no parallel eval-only implementation of search or generation.

**Non-Goals:**
- The Monitoring dashboard (separate, not yet proposed) — this change doesn't touch it.
- Any web-triggered regeneration — the in-app page is read-only; generation stays CLI-only.
- Any database schema change — no new tables, no new columns, anywhere in this change.
- Automatically picking a replacement module when the swap preflight fires — flagged for a human decision, not auto-selected.

## Decisions

**Single `data/ground_truth.csv`, not one file per question kind.** Columns: `id, module_fqcn, chunk_type (parameter|overview), stable_id, question, expected_type, expected_default, expected_choices, expected_deprecated, expected_alternative, ansible_core_version, generated_at` — the parameter and deprecation-overview slices share one schema with nullable columns for whichever fields don't apply. Considered two separate CSVs (one per question kind): rejected — both eval tasks need both slices anyway (retrieval eval doesn't care about the distinction at all), so splitting the file would only add a second artifact to keep pinned and loaded in sync for no benefit.

**Expected values are read from the app's own ingested data, not asked of the LLM.** Ground-truth generation calls RubyLLM's structured-output completion once per selected chunk to produce 2-3 *question phrasings* only — the `expected_type`/`expected_default`/`expected_choices`/`expected_deprecated`/`expected_alternative` values are pulled directly from `AnsibleModule#raw_doc`/`Chunk` (the same structured data the chunker itself was built from), not generated or transcribed by the LLM. This makes ground truth correct by construction for the checkable fields; the LLM's only job is natural-language phrasing, which is the one part that genuinely needs generation. Considered asking the LLM to extract both question and expected values from the chunk's rendered text: rejected as strictly worse — it adds a transcription-error risk for data the app already has in structured form.

**Module-swap preflight warns and continues, it doesn't auto-substitute or abort.** At the start of ground-truth generation, each of the 6 hardcoded module FQCNs is looked up in the currently ingested `AnsibleModule` set. A missing module prints a warning (naming it, and pointing at `docs/evaluation-results.md` for how to record a swap) and generation proceeds for the remaining present modules, rather than aborting the whole run. Picking the replacement module is left to a human editing the hardcoded list — the original 6 were chosen for deliberate scenario diversity (see `PLAN.md`), which is exactly the kind of real-consequence judgment call this project's own conventions reserve for a person, not a script.

**Retrieval eval and the "RAG" arm of LLM eval exercise production code paths directly, not re-implementations.** Retrieval eval calls `Retrieval::KeywordSearch`/`VectorSearch`/`HybridSearch`/`RerankerClient` per question exactly as `SearchAnsibleDocs` does, and checks whether each question's `stable_id` appears in the top-K results. LLM eval's RAG condition runs a fresh single-exchange `Chat` with `SearchAnsibleDocs`/`GetModuleDetails` registered as tools — the same registration `ChatResponseJob` performs — so the RAG arm is exercising the live app's own tool-wiring, not a parallel copy of it. The no-RAG condition is the same `Chat` setup with no tools registered.

**Two judges, not three — deprecation questions are judged by `param_accuracy`, not a new judge type.** `param_accuracy` already returns CORRECT/INCORRECT/NOT_STATED against an expected value; for a deprecation question that expected value is `expected_deprecated`/`expected_alternative` instead of `expected_type`/`expected_default`/`expected_choices`. Keeps the judge count matching what the proposal states (generic relevance + domain-specific accuracy) rather than growing a third judge for a question subtype.

**Compositional eval needs no LLM judge at all — all three checks are deterministic.** Revised during implementation: the original plan described a "third judge" for this, but on closer look none of the three checks (YAML syntactic validity, whether referenced module/parameter names exist in the ingested corpus, whether required parameters are present for the module used) are actually judgment calls — each has one unambiguous right answer computable directly from data already on hand:
- YAML validity: `YAML.safe_load` either succeeds or raises — a parse check, not a judgment.
- Real-name existence: a lookup against `AnsibleModule`/`Chunk` data (as originally planned).
- Required-parameter presence: once the YAML is parsed, the module key identifies which `AnsibleModule`, whose `raw_doc` options with `required: true` give an exact set to check the task's provided parameter keys against — also a lookup, not a judgment.

The only LLM involved in compositional eval is the *generation* step (the live agent loop producing the task YAML) — checking its output is pure verification against known facts, so introducing a judge call here would add non-determinism and cost to a step that doesn't need it. Considered keeping an LLM judge for the required-parameter check on the theory that parameter usage might be indirect (loops, vars): rejected for this eval's actual scope — 6 hand-picked, single-outcome prompts — where the generated task's module invocation is expected to be direct and parseable.

**One `data/eval_results.json`, written by a chained `eval:all` task.** Top-level `generated_at`/`ansible_core_version`, then one key per eval type (`retrieval`, `llm`, `compositional`). A single file gives the in-app page exactly one results artifact to check for presence/absence, rather than three independently-missing files with their own partial-state handling.

**The in-app page reads files directly at request time — no caching, no background pre-render.** `EvaluationsController#show` does a plain `CSV.read`/`JSON.parse` against `Rails.root.join("data/...")` on each request. Traffic to this page is low and files are small (hundreds of rows / a small JSON blob), so caching would be optimizing a cost that doesn't exist yet.

**`LlmEvaluator` runs rows in bounded batches of threads, not sequentially.** Added after live verification showed 450 questions × 6 calls each (RAG + no-RAG generation, 2 judges each) is the dominant cost of the whole pipeline, and every row is fully independent of every other row. `BATCH_SIZE = 5` — sized to the default ActiveRecord connection pool (`RAILS_MAX_THREADS`-or-5 in `database.yml`), not higher, because a RAG-condition row can indirectly hit the DB through `SearchAnsibleDocs`; going wider would need a pool bump to avoid connection-checkout timeouts, which this change doesn't make. Each thread wraps its work in `ActiveRecord::Base.connection_pool.with_connection` so its checked-out connection is returned immediately rather than left for Rails' reaper to notice. Considered also parallelizing *within* a row (RAG/no-RAG generation concurrently, then all 4 judge calls concurrently) for a further ~3x per-row reduction: rejected for now — it multiplies the concurrency dimensions (batch width × per-row fan-out) in a way that makes reasoning about total in-flight HTTP calls and rate-limit exposure harder, for a benefit smaller than the batch-level win already captured. `RetrievalEvaluator`/`CompositionalEvaluator` were left sequential — retrieval eval has no LLM cost (local search + one reranker call per question) and compositional eval is only 6 calls total, so neither is the bottleneck this was worth optimizing.

**Revised during live verification — three fixes found by actually running the pipeline, not just reading the code:**
- **Compositional prompts must explicitly request a fenced ` ```yaml ` block.** Without it, the agent answers in prose with an unfenced YAML snippet embedded in it, which `CompositionalChecker`'s fenced-block extraction can't isolate — confirmed live, every one of the 6 compositional answers came back `yaml_valid: false` before this, not because the YAML itself was wrong, but because extraction found nothing to parse. `CompositionalEvaluator::FORMAT_INSTRUCTION` is appended to each prompt at ask-time, kept separate from `PROMPTS`' documented task wording since it's an eval-mechanics concern, not part of the task itself.
- **`eval:llm`'s sample-size limit must be a stratified sample, not a raw prefix.** `ground_truth.first(limit)` sampled 18/18 questions from a single module (`ansible.builtin.apt`) in a live run — the CSV's row order follows ingestion order, not any deliberate ordering, so a prefix silently defeats the whole point of the 6-module diversity (a small sample wouldn't even include `apt_key`'s one deprecation question). Fixed by extracting `Eval::StratifiedSample.take(rows, limit, by:)` — round-robins across the grouping key so a sample of size N always touches min(N, module count) distinct modules first. Kept as a standalone, directly unit-testable pure function (no LLM/HTTP stubbing needed), the same pattern as `Eval::HitRateMrr`.
- **Local test runs were clobbering the real, checked-in `data/ground_truth.csv`.** `GroundTruthGenerator` originally always wrote to `GroundTruth::DEFAULT_PATH`, so any test exercising it — even indirectly through the full suite — silently overwrote the real generated file with test-fixture data (confirmed live: a local `bin/rails test` run left the file at 23 rows instead of 450). Fixed by giving `GroundTruthGenerator.new` an optional `path:` parameter (defaulting to `DEFAULT_PATH`), with the test suite always passing a `Tempfile` path. This is the kind of test/production path collision the project's testing conventions exist to catch — it wasn't caught by the unit tests themselves (each ran against its own path already, by virtue of stubbing being per-test-file... except this one file didn't stub the path at all), only by noticing the real file's row count didn't match what generation had just produced.
- **Keyword-only retrieval scored `hit_rate ≈ 0` across all 450 questions — a real finding, not a bug.** Investigated rather than assumed: `Chunk.search` uses `plainto_tsquery`, which ANDs every term in the query. Ground-truth questions are LLM-phrased natural language (10+ words, often including the module's dotted FQCN as one of those words), and requiring every single term to match is an unreasonably strict bar that chunk content essentially never clears. Confirmed keyword search still works fine for short, deliberately keyword-style queries (2-3 words) — this is specifically a mismatch between `plainto_tsquery`'s AND semantics and verbose natural-language questions. Left as-is (not a bug in this change's scope, and not something to silently "fix" by loosening the retrieval eval's own query phrasing to flatter keyword search) — reported honestly in `docs/evaluation-results.md` as a legitimate, concrete illustration of why hybrid+rerank outperforms any single strategy in this application's actual usage pattern.

## Risks / Trade-offs

- **LLM eval is a real API cost/time sink even at 6-module scope** — ~300-450 parameter questions plus a handful of deprecation questions, each needing 2 generations (RAG/no-RAG) × 2 judge calls, is on the order of a thousand-plus real completions for one full run. → `eval:llm` accepts an optional sample-size limit for fast iteration during development; the full, undocumented-limit run is what actually produces the committed `eval_results.json`.
- **Ground-truth phrasing quality is itself an LLM output** — an ambiguously-phrased generated question could make a correct answer score as wrong, even though the expected values themselves are correct by construction. → Spot-check a sample of generated questions by hand before committing a ground-truth regeneration, consistent with this project's existing habit of verifying empirically rather than trusting generated output blindly.
- **The swap preflight only checks module presence/removal, not whether a still-present module's parameter values have drifted** (e.g. a default value changing in a new release without the parameter being renamed or removed) — a genuine gap this design doesn't close. → Not automated; mitigated at the process level, since regeneration is already a deliberate, manually-triggered, hand-reviewed step per the pinning decision in `PLAN.md`, not something assumed to stay correct indefinitely between runs.

## Migration Plan

Purely additive — new rake tasks, a new controller/route/view, and new generated data files; no database migration anywhere in this change (see Non-Goals). The one behavioral change to existing code (`Ingestion::Chunker#overview_chunk` now including deprecation content) takes effect on the *next* ingestion run, which per the existing `ansible-ingestion` capability's atomic-replace requirement fully replaces all chunks at once — there's no partial-migration state to handle for existing chunk data.
