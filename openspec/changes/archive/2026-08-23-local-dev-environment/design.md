## Context

See `proposal.md` for motivation. Relevant current state, confirmed by direct inspection rather than assumed (per this project's working style):

- `mise.toml` currently declares `uv`/`python`/`ruby`/`claude`/`npm:@fission-ai/openspec` in `[tools]` and only `curl`/`jq` in `[bootstrap.packages]`.
- `rails_app/config/database.yml`'s `development`/`test` blocks already point at `localhost:$POSTGRES_PORT` with `.env.example`-matching credential defaults — no changes needed there.
- `app/services/embedding_client.rb:8` defaults `EMBEDDER_URL` to `http://embedder:8000` (Docker-internal DNS name); confirmed `EMBEDDER_URL` is not present anywhere in `docker-compose.yml`'s `web`/`worker` `environment:` blocks, so it isn't passed into containers even if set in `.env`.
- `rails_app/bin/docker-entrypoint` runs `bin/rails db:prepare` + `bin/rails db:grafana_reader:ensure` on every container boot; this script is Docker-only and never runs for a locally-started process.
- `config/initializers/ruby_llm.rb` does `ENV.fetch("OPENAI_API_KEY")` — raises and hard-crashes boot if unset, in any environment.
- `rails_app/Dockerfile`'s `base` stage: `apt-get install build-essential libpq-dev` (for the `pg` gem). Its `worker` stage: `uv tool install ansible-core` (unpinned, refreshed by the separately-planned weekly CI workflow).
- `embedder/pyproject.toml` already pins CPU-only `torch` via `[[tool.uv.index]]`/`[tool.uv.sources]` — this applies to any `uv sync`, container or local, no changes needed there.
- Directly tested: mise's registry maps `ansible-core` to a `pipx:` backend, but running `mise install ansible-core@latest` showed its first real step is `uv tool install ansible-core==<version>` — mise prefers `uv` over `pip`/`pipx` internals when `uv` is present. So declaring it in `[tools]` is not a "pipx instead of uv" compromise; it's the same underlying install mechanism as `Dockerfile`'s `worker` stage.
- Directly tested: `build-essential` and `libpq-dev`/`gcc`/`make` happened to already be present on this sandbox machine — that's this machine's pre-existing state, not something a fresh clone is guaranteed to have, which is why they're being declared explicitly rather than left implicit.

## Goals / Non-Goals

**Goals:**
- A contributor can run `web`/`worker`/`embedder` as local processes, with Postgres/Grafana still via `docker compose`, using only `mise`/`uv`-provisioned tools.
- Local and containerized paths stay independent — nothing in this change alters `docker-compose.yml`, any Dockerfile, or container-path behavior.
- Every new local-only piece (tasks, `Procfile.dev` line, `.env` sourcing) is declared/discoverable via `mise`, not left as README-only prose to remember.

**Non-Goals:**
- Fixing the README's other, unrelated staleness (the removed `prepare_db` service, missing Grafana docs) — tracked separately in PLAN.md's "Remaining work," out of scope here.
- Changing `config/recurring.yml` — local `worker` intentionally never auto-fires the weekly ingestion job; `mise run ingest` is the manual trigger, matching today's already-documented Docker equivalent.
- A unified single-command launcher that starts Postgres/Grafana/embedder/web/worker together — three separate steps (docker compose subset, `uv run uvicorn`, `bin/dev`) is the deliberate shape, matching PLAN.md's existing "infra you don't want to install locally, not code you're iterating on" split.
- Solving macOS's `build-essential`/Xcode Command Line Tools gap programmatically — documented as a manual prerequisite instead, since `mise`'s `brew:` backend cannot install it.

## Decisions

**`ansible-core` via `mise`'s `[tools]` table, not a custom task.** Verified directly (see Context) that this uses `uv tool install` under the hood already — a custom `uv tool install ansible-core` task would be redundant with what declaring the tool already gets for free, and would lose `mise`'s own version tracking/`mise ls`/`mise bootstrap` integration for no benefit.

**Root-level shared Python `pyproject.toml` (merging `embedder`'s ML deps with `ansible-core`) was considered and rejected.** `ansible-core` is a CLI tool invoked by Ruby via subprocess (`AnsibleDocClient`), not a Python library dependency of anything. `uv tool install`/mise's `[tools]` puts its binary in a PATH-visible location for exactly that reason; a project-dependency-in-a-venv approach would need extra `PATH` wiring for the separate Ruby `worker` process to find it, for no offsetting benefit. It would also re-couple `embedder` (ML-serving only) with ingestion's CLI tooling — reversing a decision CLAUDE.md/PLAN.md already document as deliberate (domain cohesion over Python-purity: `ansible-core` moved *out* of the embedder once already) — and would complicate both Dockerfiles' build contexts, since `embedder`'s slim image would need dependency-group filtering to avoid pulling in `ansible-core`'s deps, and vice versa.

**`db:prepare` and `ingest` as `mise` tasks, not README-only commands.** Matches this project's existing bias toward `mise`-orchestrated local tooling (see `dev-toolchain`'s existing requirements) and keeps them discoverable via `mise tasks` rather than a copy-pasted shell command a contributor has to remember and re-find in the README each time.

**Reversed: `dotenv-rails` is used instead of sourcing `.env` from `bin/dev`.** Originally decided to have `bin/dev` source `.env` directly (matching this project's existing `set -a && source ../.env && set +a` convention for local rake/test runs) to avoid a new dependency. Revisited and reversed, at the user's explicit request: a Gemfile-declared `dotenv-rails`, scoped to `group :development, :test`, loads `.env` automatically for every local entrypoint — `bin/dev`, `rails console`, `rails runner`, tests — not just the one `bin/dev` invocation, and is the Rails-idiomatic mechanism a reviewer would expect. Trade-off: `.env` lives at the repo root, one directory above `rails_app/` (dotenv-rails' default search root), so `Dotenv::Rails.files` needs an explicit override in `config/application.rb` (set before `Bundler.require`) — a one-time, non-obvious piece of config, in exchange for the gem handling every local Ruby entrypoint automatically rather than just the one covered by a `bin/dev` edit. Scoped to `development`/`test` only so it never activates inside the `web`/`worker` Docker images, which already get real env vars injected directly by `docker-compose.yml`'s `environment:` blocks.

**`EMBEDDER_URL` added to `.env.example` rather than hardcoding a development-environment default in `embedding_client.rb`.** Confirmed the variable isn't read anywhere in `docker-compose.yml`, so this is a zero-risk addition — no conditional `if Rails.env.development?` branching needed in application code, and the existing `ENV.fetch("EMBEDDER_URL", "http://embedder:8000")` default keeps working unchanged for the containerized path.

**Postgres and Grafana stay in `docker compose` even for local dev.** Already decided in PLAN.md ("infra you don't want to install locally, not code you're iterating on") — not reopened here.

## Risks / Trade-offs

- [`build-essential`/libpq-dev happened to already be present on this dev machine, masking whether the bootstrap declaration is actually sufficient on a truly fresh machine] → Mitigation: the `mise bootstrap` scenario in the spec delta is testable independently (e.g. in a scratch container or VM) before relying on it for the eventual "fresh clone" reproducibility pass; not blocking this change, but worth re-verifying then.
- [Two independent ways to run the app (local processes vs. Docker) can drift out of sync over time — e.g. a new required env var added to `docker-compose.yml`'s `environment:` block but not to `.env.example`/local docs] → Mitigation: none automated in this change; accepted as an ongoing manual-discipline cost, consistent with this project's existing single-`.env`-file secrets story.
- [`mise run ingest` requires `embedder` already running locally, but nothing enforces that ordering] → Mitigation: documented in the task's own description/help text and in the README's ordered steps, matching how `worker`'s Docker `healthcheck`-based ordering was itself already accepted as non-enforced in this sandbox (see CLAUDE.md's podman-quirks section) — a documented convention, not a hard guarantee, is consistent with this project's existing tolerance for that gap.

## Discovered during implementation

Verifying task 4.6 live (`bin/dev` with a locally-run `worker`) surfaced a gap this design didn't anticipate: `worker` crashed immediately with `PG::UndefinedTable: relation "solid_queue_processes" does not exist`. Root cause, confirmed by reading the actual files rather than assumed:

- `rails_app/config/database.yml`'s `development`/`test` blocks were a single flat database each — unlike `production`, which splits into `primary`/`cache`/`queue`/`cable`. Solid Queue's tables live in `db/queue_schema.rb`, loaded only for a database actually declared as `queue` in the current environment's `database.yml` block — which `development` never had.
- `rails_app/config/environments/development.rb` never set `config.active_job.queue_adapter = :solid_queue` or `config.solid_queue.connects_to` — only `production.rb` did. Development was relying on Rails' default `:async` in-process adapter, where whatever process calls `.perform_later` also runs the job inline — meaning a separate `worker` process was never a meaningful part of the development story before this change, regardless of `Procfile.dev`.

Together this means: **a locally-run `worker` process could never have worked, in any prior state of this repo** — not a regression introduced here, but a gap this change's own goal (local `web`/`worker` processes) was the first thing to actually exercise. Fixed by mirroring `production`'s existing pattern into `development`/`test`: the same `primary`/`cache`/`queue`/`cable` split in `database.yml` (with `development`/`test`'s existing `host: localhost`/`ENV.fetch`-with-defaults credential style, not `production`'s `ENV[]`-no-fallback style), and the same two `queue_adapter`/`connects_to` lines in `development.rb`. Confirmed working end-to-end: a locally-run `worker` registers a real `SolidQueue::Process` heartbeat (Supervisor/Dispatcher/Worker), and a real chat message sent through a locally-running `web` process gets a grounded reply produced by that local `worker`, calling the local `embedder` via `EMBEDDER_URL`.

Not extended to `test`'s `queue_adapter` — Rails' test environment already forces `:test` (synchronous, in-memory) regardless of `config.active_job.queue_adapter`, so there's nothing to change there; only the `database.yml` split was needed for `test` (schema consistency, no behavior change since the test suite doesn't currently exercise `SolidQueue::Record` directly).

A second, separate gap surfaced right after: running the actual test suite (a step not in the original task list, but standard practice before calling any Rails config change done) failed 14 tests with `WebMock::NetConnectNotAllowedError`, because `dotenv-rails` was originally scoped to `group :development, :test` — the `test` run picked up the real repo-root `.env`, including this change's own new `EMBEDDER_URL=http://localhost:8000`, which overrode `EmbeddingClient`'s code-level default (`http://embedder:8000`) that existing tests' `WebMock` stubs were written against. This is a real design mistake in the original "dotenv-rails covers every local entrypoint... tests" framing, not a fluke of this one variable — any future addition to `.env` would risk the same class of collision, because tests were silently inheriting a real developer's full local config instead of staying hermetic. Fixed by moving `dotenv-rails` to `group :development` only, and adding a dummy `ENV["OPENAI_API_KEY"] ||= "dummy"` stand-in at the top of `config/environments/test.rb` (mirroring the same "dummy value is fine, real calls are stubbed" reasoning `Dockerfile`'s asset-precompile step already uses) so `bin/rails test` still needs zero manual setup — it just gets there via a fixed stand-in instead of the real `.env`, rather than regressing to needing `.env` sourced manually the way local test runs did earlier this session. Re-ran the full suite with `env -i` (no exported vars, no `.env` sourcing): 94/94 passing.

A third gap, same underlying cause, surfaced by the user actually using the app through `bin/dev` (posting a real chat message and needing a manual page refresh to see the reply): `config/cable.yml`'s `development` block used Action Cable's `async` adapter — confined to a single process by design (the file's own comment already warned about this, for console-broadcast debugging, not for this scenario). Once `worker` became a real separate process, a Turbo Streams broadcast fired from `worker` after a job finished could never reach `web`'s Action Cable server, which is what the browser's websocket actually connects to — the message itself saved correctly (visible on refresh, which re-renders from the database), it just never got pushed live. Fixed the same way as the other two: mirrored `production`'s `solid_cable` config into `development`, reusing the `cable` database connection already added above.

A fourth item, user-requested rather than discovered: Grafana's `datasources/postgres.yml` was hardcoded to `database: rails_app_production`, so none of the local `bin/dev` chat traffic above was visible in the Chat Monitoring dashboard, regardless of any of the fixes above. Added a second datasource (`postgres_grafana_reader_dev`, same Postgres container and `grafana_reader` role — already granted access to `rails_app_development`'s tables by `mise run db:prepare`, no extra step needed) and a dashboard-level `datasource` template variable (Grafana's standard mechanism for this) so the existing dashboard JSON can point at either database via a dropdown, rather than maintaining a near-duplicate second dashboard file. Verified via Grafana's own datasource health-check API (`Database Connection OK` against `rails_app_development`).

**Found while verifying the datasource fix, explicitly NOT fixed in this change — out of scope, flagged for the user separately**: `RetrievalLog` rows (what every Chat Monitoring panel queries) are only created when `ChatResponseJob` sees `search_tool.retrieved_chunks.any?` — i.e., only turns where the LLM specifically calls the `SearchAnsibleDocs` tool and gets hits (`app/jobs/chat_response_job.rb:18`). Neither the live app (`ChatResponseJob`) nor the LLM-eval harness (`Eval::LlmEvaluator`) ever calls `.with_instructions(...)` on the chat — there is no system prompt anywhere in the codebase, despite PLAN.md's "Agent loop" section describing one ("search broadly first, then call `GetModuleDetails` once the exact module is identified"). Confirmed directly: even PLAN.md's own canonical example question ("what does the mode parameter of the copy module default to") produces a `get_module_details`-only tool call, no `search_ansible_docs` call, hence no `RetrievalLog` row. This means Monitoring's `retrieval_logs`-based panels likely undercount real usage significantly, and the existing `monitoring` spec's own wording ("a new chat message is sent and answered, producing a new `RetrievalLog`") is not actually guaranteed by current code for every answered message. This is a RAG-flow/agent-behavior gap, not a dev-environment one — out of scope for this change; worth its own investigation into whether to add the missing system prompt, decouple monitoring logging from a specific tool call, or both.

A sixth item, found while finally executing tasks 4.1/4.2 for real (a fresh `debian:bookworm-slim` container, no pre-existing packages, confirmed via `dpkg -l` before `mise bootstrap` ran) rather than leaving them unchecked: `bundle install` succeeded and `ansible-doc --version` worked, confirming `mise bootstrap` alone is sufficient — but the `pg` gem specifically did **not** compile a native extension against `libpq-dev`. Bundler installed the prebuilt `pg (1.6.3-x86_64-linux)` platform gem straight from rubygems.org (already present as an alternate platform entry in `Gemfile.lock`, resolved automatically since Ruby 4.0.6 matches its supported ABI range), and `ldd` on its `pg_ext.so` shows it links `libpq-ruby-pg.so.1` — a copy of libpq vendored inside the gem itself, not the system `libpq.so` `libpq-dev` would provide. `puma`/`bootsnap`/`rbs`, by contrast, did compile "with native extensions" using `build-essential`, confirming that package is genuinely exercised. This means the assumption "the `pg` gem needs `libpq-dev` to build its native extension" — stated in `rails_app/Dockerfile`'s own comment since `2026-08-08-rails-app-scaffold`, and repeated in this change's README edit — is not currently true for the `x86_64-linux`/`aarch64-linux` platforms Bundler resolves prebuilt gems for; it would only become true again if a future platform/musl variant lacked a prebuilt `pg` gem and Bundler fell back to compiling from source. Not changed here: removing `libpq-dev` would be a correct, minor cleanup, but it's a repo-wide, pre-existing assumption predating this change (present in the containerized `Dockerfile` too, out of this change's `Impact` file list) — not something this change's own local-process goal introduced or is blocked by. Flagged for a possible future small cleanup change, not fixed in-place here.

## Migration Plan

Purely additive — no existing files are removed, no schema changes, no container-path behavior changes. Rollback is a plain revert of the touched files (`mise.toml`, `rails_app/Procfile.dev`, `rails_app/Gemfile`, `rails_app/config/application.rb`, `.env.example`, `README.md`) with no data or infrastructure to unwind.
