## Context

`mise.toml` currently only declares `claude` and `npm:@fission-ai/openspec` (both `"latest"`). The `embedder-sidecar` change (in progress) needs `uv`, `python`, `curl`, and `jq` on the host to scaffold and verify the FastAPI sidecar, and nothing declares or documents how to get them yet. The user develops across two machines — a Linux box and a Mac — so the package-manager story needs to work on both, not just the one this session runs on. Verified directly against the `mise` binary installed on this machine (version 2026.8.1) rather than assumed:
- `mise registry` confirms `uv` and `python` are valid top-level tool names (`uv` → `aqua:astral-sh/uv` / `asdf:asdf-community/asdf-uv` / `pipx:uv`; `python` → `core:python`).
- `mise bootstrap packages use --dry-run apt:curl apt:jq` confirms the exact config shape mise writes: a `[bootstrap.packages]` table with `"apt:curl" = "latest"` / `"apt:jq" = "latest"` entries.
- `mise bootstrap --help` confirms `mise bootstrap` runs, in order: plugins → **packages** → repos → dotfiles → shell-activation → macOS defaults → macOS launchd agents → Linux systemd units → user login shell → **tools** → a project `bootstrap` task → final hooks. Steps with nothing declared for them are no-ops, so a project that only populates `[tools]` and `[bootstrap.packages]` (this change) safely skips everything else.
- **A behavior that contradicts mise's own published docs, found by direct testing, not assumed from documentation:** declaring both `apt:curl` and `brew:curl` in `[bootstrap.packages]` and running `mise bootstrap packages use -y apt:curl apt:jq brew:curl brew:jq` on this Linux machine did **not** skip the `brew:` entries. Instead `mise` attempted to bootstrap Homebrew itself (Linuxbrew, at `/home/linuxbrew/.linuxbrew`), which requires `sudo` and failed here only because no TTY was available for the password prompt. Search-engine-summarized docs claim "entries for a manager that isn't available on the current machine are not acted on" — that claim does not hold for `brew:` on Linux specifically, because Homebrew genuinely *is* installable on Linux (unlike, say, `apt` on macOS, which has no equivalent bootstrap path). This is a real, reproducible gap between documented and observed behavior in this mise version, not a misunderstanding on the user's part.
- The fix, also verified directly: `mise settings get system_packages` shows `{ sudo = true }` is the default, and there's a `system_packages.managers` setting to restrict which managers `mise` acts on. Setting `system_packages.managers = ["apt"]` (via a `[settings]` block) made `mise bootstrap packages status` correctly report the `brew:` entries as `skipped (excluded by the system_packages.managers setting)`, with no Linuxbrew-bootstrap attempt.
- Where that setting lives was also tested empirically, because docs claimed OS-specific files (`mise.linux.toml`, `mise.macos.toml`) compose automatically per-OS — that did **not** happen here: a `mise.linux.toml` sitting next to `mise.toml` was silently ignored (absent from `mise config ls`'s output) on this actual Linux machine. A `mise.local.toml`, by contrast, **was** picked up automatically (present in `mise config ls`, and its `system_packages.managers` setting took effect). `mise.local.toml` is also mise's documented convention for personal, machine-specific, gitignored overrides — a good fit regardless, since the two machines need different values for the same setting.

## Goals / Non-Goals

**Goals:**
- `mise.toml`'s `[tools]` table gains `uv` and `python`, both `"latest"` — consistent with the existing `claude`/`openspec` entries' versioning convention.
- `mise.toml`'s `[bootstrap.packages]` table gains `apt:curl`, `apt:jq`, `brew:curl`, `brew:jq`, all `"latest"` — works on both the Linux box (apt) and the Mac (brew).
- Each machine restricts itself to its own package manager via a gitignored, per-machine `mise.local.toml` setting `system_packages.managers`, so `brew:` entries on Linux (and, symmetrically, `apt:` entries on macOS) are cleanly skipped rather than triggering an unwanted cross-platform bootstrap attempt.
- A single `mise bootstrap` command takes a fresh clone from "has `mise` (and a correctly-configured `mise.local.toml`) installed" to "has every tool this project currently needs."
- `README.md` exists with exactly one section, **Development**, documenting that command, the `mise.local.toml` step, and linking to mise's own install instructions.

**Non-Goals:**
- No `[bootstrap.repos]`, `[dotfiles]`, `[bootstrap.macos]`, or `[bootstrap.linux.systemd]` sections — this change only uses the `packages` and `tools` steps of `mise bootstrap`; the rest of the bootstrap pipeline stays unconfigured (and therefore a no-op) for now.
- No other `README.md` sections (project overview, architecture, usage) — explicitly scoped to *Development* only, per this change's request; the rest of the README gets filled in as the corresponding capabilities (ingestion, chat UI, etc.) land in later changes.
- No support for package managers beyond `apt`/`brew` (e.g. `dnf`, `apk`) — scoped to the user's actual two development machines.
- No pinned/exact versions for any of the four new package entries or the two new tool entries — matches the existing `mise.toml` convention of `"latest"` for both current entries; not introducing a new versioning policy here.
- Not relying on `mise.linux.toml`/`mise.macos.toml` auto-composition for the `system_packages.managers` split, since that didn't work as documented when tested directly on this machine (see Context) — using the verified-working `mise.local.toml` mechanism instead, at the cost of a one-time manual step per machine.

## Decisions

**1. `curl`/`jq` via `[bootstrap.packages]` (`apt:` and `brew:`), not `[tools]` (a cross-platform backend like `aqua`).**
- `mise` *can* manage `curl`/`jq` as regular tools too (both are aqua-registry-installable, OS-independent binaries) — that path was considered and would sidestep the whole `apt`/`brew` split below with a single OS-independent entry each. Going with `[bootstrap.packages]` instead because that's the explicit mechanism requested: real system packages via each machine's actual OS package manager, verified working via `mise bootstrap packages use --dry-run apt:curl apt:jq` on this machine.

**2. Both `apt:` and `brew:` entries declared in the shared `mise.toml`; per-machine restriction lives in a gitignored `mise.local.toml`, not in `mise.toml` itself.**
- Alternative considered: rely on `mise.linux.toml`/`mise.macos.toml` auto-composing per-OS, as the general docs describe. Rejected after direct testing showed `mise.linux.toml` was not picked up at all on this machine (absent from `mise config ls`) — building the design around undocumented-in-practice behavior would leave the Mac side unverifiable and likely broken too.
- Alternative considered: only declare `apt:` entries and let the user manually `brew install curl jq` on the Mac, outside `mise` entirely. Rejected — it would mean `mise bootstrap` silently under-provisions on macOS with no signal that anything's missing, and defeats the point of a single declared toolchain.
- Chosen approach: `mise.toml` (shared, committed) declares all four package entries; each machine gets its own `mise.local.toml` (gitignored, uncommitted, mise's documented convention for personal/machine-specific overrides) setting `[settings] system_packages.managers = ["apt"]` on Linux or `["brew"]` on macOS. Verified directly: with that setting in `mise.local.toml`, `mise bootstrap packages status` correctly shows the other platform's entries as `skipped (excluded by the system_packages.managers setting)` rather than attempting to bootstrap the other manager. The cost is a one-time manual step per machine (creating the local file) instead of it being fully automatic — acceptable given the verified alternative doesn't work.

**3. `mise bootstrap` (not `mise install`) is the documented command.**
- `mise install` only handles `[tools]`; it wouldn't install the `[bootstrap.packages]` entries. `mise bootstrap` runs both steps (and everything else, all currently no-ops per Context above), so it's the one command that fully provisions the project regardless of what sections get added to `mise.toml` later — the README's instruction stays correct as the project grows without needing an update every time a new bootstrap section is introduced.

**4. README gets exactly one section for now: Development.**
- Matches the explicit scope of this change. Assumes the reader already has `mise` installed (linking to `https://mise.jdx.dev/installing-mise.html` for that one prerequisite step, verified as the current official install-docs URL), documents the one-time `mise.local.toml` step, and gives them `mise bootstrap` as the next command.

## Risks / Trade-offs

- **[Risk] Skipping the `mise.local.toml` step on Linux, then running `mise bootstrap`, triggers an unwanted Homebrew (Linuxbrew) install attempt requiring `sudo`** → Mitigation: the README documents `mise.local.toml` as a required step, not optional, directly because of this verified behavior; `tasks.md` includes a verification step that deliberately checks the un-configured case fails/prompts as expected, so this isn't just asserted but confirmed.
- **[Risk] The `mise.local.toml` mechanism can't be verified on macOS in this session** (no Mac available here) — the Linux side (apt-only via `system_packages.managers = ["apt"]`) is directly verified; the macOS side (`["brew"]`) is not. Mitigation: symmetric design (same setting, same mechanism, just a different value) minimizes surprise; flagged as an open question below to confirm the first time `mise bootstrap` actually runs on the Mac.
- **[Risk] `mise bootstrap` runs more steps than "just install my tools"** (plugins, repos, dotfiles, etc.) → Mitigation: none of those sections exist in `mise.toml`, so each step is a fast no-op; confirmed by reading `mise bootstrap --help`'s step list against the current (pre-change) `mise.toml` contents.
- **[Trade-off] `"latest"` for all six new entries (two tools, four packages), no pinning** → consistent with the existing two entries' convention; sacrifices exact-version reproducibility (a contributor bootstrapping today vs. months later could get different patch/minor versions). Acceptable — none of these are version-sensitive for this project's usage so far, and introducing pinning policy is out of scope for this change.
- **[Trade-off] `mise.local.toml` is a manual, undocumented-by-mise-itself step per machine** → the alternative (relying on `mise.linux.toml`/`mise.macos.toml` auto-composition) is what the docs actually recommend for this exact scenario, but it didn't work when tested directly here. Manual-but-verified beats automatic-but-unverified.

## Migration Plan

- Purely additive: two new tables/entries appended to the existing `mise.toml` (its current `claude`/`openspec` entries are untouched), a new gitignored `mise.local.toml` (created locally, not committed), plus one new `README.md` file.
- Rollout (Linux): create `mise.local.toml` with `system_packages.managers = ["apt"]`, run `mise bootstrap` from the repo root, confirm `uv`, `python`, `curl`, `jq` are all on `PATH` and `mise bootstrap packages status` shows `brew:` entries as skipped, not missing.
- Rollout (macOS, first time only): create `mise.local.toml` with `system_packages.managers = ["brew"]`, run `mise bootstrap`, confirm the same four tools/packages land and `apt:` entries are skipped.
- Rollback: revert the `mise.toml` diff, delete the local `mise.local.toml` and `README.md`. No installed-tool cleanup needed — `mise uninstall`/`mise bootstrap packages prune` can remove them from the machine if desired, but leaving them installed is harmless.

Confirm the first time `mise bootstrap` runs on the Mac; not expected to be a blocking surprise since `apt` has no Linux-style "install it via another manager" bootstrap path on macOS to begin with, but worth a real check.
