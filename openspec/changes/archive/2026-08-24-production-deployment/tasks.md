  - **Discovered during implementation**: the remote-builder build itself succeeded first try (ran on the VM's now-installed Docker daemon over the SSH context), but the push failed with `denied` — read `Kamal::Commands::Builder::Remote#login_to_registry_locally?` (returns `false`, unconditionally) and confirmed `Kamal::Cli::Build#push` genuinely never calls `docker login` at all for a remote builder + non-local registry combination. This isn't a Kamal bug in the sense of something to patch — buildx forwards whatever local Docker credential-store auth exists through the build session regardless of driver, so the fix is just running `docker login ghcr.io` locally once, ourselves, before `kamal build push` (not something Kamal automates for this combination).
  - **Second discovery**: the first login attempt got `denied: permission_denied: The token provided does not match expected scopes` — the fine-grained PAT initially used doesn't support GHCR at all. Confirmed directly against GitHub's own docs (`working-with-the-container-registry`): *"GitHub Packages only supports authentication using a personal access token (classic)"* — there's no "Packages" permission in the fine-grained PAT UI at all, matching what was observed. Fixed by generating a classic PAT with `write:packages` scope instead.
  - **Third discovery, found while testing the above**: sourcing `.env.production` to test the GHCR login manually hit a bash syntax error on `POSTGRES_PASSWORD` (unescaped parens) — `.kamal/secrets` sources this file the exact same way (`source ../.env.production`), so every key declared *after* `POSTGRES_PASSWORD` (`OPENAI_API_KEY`, both Grafana passwords, `ADMIN_EMAIL`, `ADMIN_PASSWORD`) was silently never being set by a real `kamal` invocation — a parse-time abort skips the rest of the file, not just that one line. Fixed by single-quoting every value in `.env.production` (verified after the fix: all 9 keys source with no error, each resolving to a non-empty value of the expected length, checked without ever printing the values themselves). Updated `.env.production.example` with an explicit comment instructing all future values to be single-quoted, since this is a `source`d bash script, not a plain dotenv file.
