## Context

Worked out via `/opsx:explore` this session. Every Kamal/Thruster mechanism below was verified by installing `kamal` (2.12.0) and `thruster` (0.1.25) as real gems and reading their source directly, plus a scratch `rails new` run with `--skip-kamal`/`--skip-thruster` omitted (to see the actual generated `Dockerfile`/`Gemfile`/`bin/thrust`) — not assumed from memory or docs alone.

**This reverses a prior explicit decision.** `rails-app-scaffold` (archived) ran `rails new rails_app --skip-docker --skip-kamal --skip-thruster`, documented as: *"this project deploys via docker-compose, not Kamal, and doesn't need Thruster's HTTP/2+asset-caching proxy in front of a single-instance capstone app."* That reasoning held when the project had no real deployment target. It no longer holds — there's now a real Debian VM, a real domain, and a need for a live, reviewable URL. Kamal and Thruster are being added back deliberately, not because the original decision was wrong at the time.

**Target environment** (user-provided, already provisioned): Debian stable, amd64, 4GB RAM / 2 vCPU / 30GB disk (10GB currently available), SSH access, domain `llm-zoomcamp-project.alfonsoalba.com` already pointing at the VM's IP.

**This also reverses this project's "one `.env` file" convention.** `rails-app-scaffold`/`setup-postgres-compose` deliberately kept a single root `.env` for every secret, local and containerized alike — that held up while "production" only ever meant "docker-compose on your own machine." It stops holding up once there's a real remote deployment: a flat `.env` can only carry one value per key, but local dev and the real VM genuinely need *different* values for the same keys (you don't want your local Postgres password to be your production Postgres password, or your laptop's file to contain the real, billed `OPENAI_API_KEY`). See Decision 5.

**`docker-compose.yml` and the local-dev workflow are untouched.** This is an additive production path — a reviewer can still `docker compose up -d --build` locally exactly as today. `openspec/specs/rails-app/spec.md` and `postgres-database/spec.md` describe that path and don't change.

## Goals / Non-Goals

**Goals:**
- A real, HTTPS, login-gated production deployment reachable at `llm-zoomcamp-project.alfonsoalba.com`.
- Preserve this project's deliberate `web`/`worker` image split (worker alone carries `ansible-core`) and `embedder`'s separate image, rather than collapsing them for Kamal's convenience.
- No new secrets store — one root `.env` stays the single source of truth.
- Zero new manual deploy-time steps for the one admin account (no `rails console` on the server).

**Non-Goals:**
- Multi-server / high-availability deployment — this is one VM, one of everything.
- A Postgres-readiness retry loop in `bin/docker-entrypoint` — explicitly rejected, see Decision 4.
- Self-service registration or password reset — explicitly out of scope, see the `authentication` capability.
- Changing anything about the local `docker compose` workflow.

## Decisions

### 1. `worker`/`embedder` stay separate images, built and pushed via build-only satellite Kamal configs, run as accessories

Checked `Kamal::Configuration::Role` and `Kamal::Configuration::Builder` directly: `servers:` roles share exactly one `image:`/`builder:` config across the whole app — there is no per-role image or build-target override in 2.12.0. Checked `Kamal::Configuration::Accessory#image`: it just reads a static `image:` string — accessories are registry-pull only, no local build support at all. Neither of Kamal's two native mechanisms fits this project's deliberate two-image split.

Resolution: three Kamal config files, one shared local registry, only one config ever runs `kamal deploy`:

```
config/deploy.yml            service: llm-zoomcamp-project       servers: {web}, proxy: {…}
config/deploy.worker.yml     service: llm-zoomcamp-project-worker    no servers:/proxy: — build+push only
config/deploy.embedder.yml   service: llm-zoomcamp-project-embedder  no servers:/proxy: — build+push only
```

Confirmed `servers:` accepts `nil` at the schema level (`Configuration::Validator::Servers`: `validate_type! config, Array, Hash, NilClass`) — but this turned out to be necessary, not sufficient. **Corrected during implementation**: a config with *neither* `servers:` nor `accessories:` fails a separate, higher-level check — `Kamal::Configuration#ensure_required_keys_present` raises `"No servers or accessories specified"` unless `raw_config.accessories.present?` when `servers:` is absent. Confirmed the hard way: `kamal build push -c config/deploy.worker.yml` genuinely failed with that exact error before this fix, not just `kamal config`. Resolution: each satellite config carries a small `accessories:` stub mirroring its own real accessory entry in the main `config/deploy.yml` — present only to satisfy this check, never itself booted (`kamal accessory boot/reboot` always targets the main config). A comment in each satellite file says so explicitly, including the "must be kept in sync" caveat. Workflow unchanged otherwise: `kamal build push -c config/deploy.worker.yml` and `-c config/deploy.embedder.yml` push to the shared registry; the main `config/deploy.yml`'s real `accessories:` block references those tags. `worker`/`embedder` builders: `context: rails_app, dockerfile: rails_app/Dockerfile, target: worker|<none>, arch: amd64` / `context: embedder, dockerfile: embedder/Dockerfile, arch: amd64` — same context/target split `docker-compose.yml` already uses.

Also discovered: `kamal config` (the YAML-dump display command) itself has an edge-case bug for accessories-only configs — its `Configuration#to_h` calls `primary_host`/`service_with_version`, which dereference `primary_role` unconditionally; with no `servers:` at all, that's `nil`, and `to_h` raises `NoMethodError: undefined method 'keys' for nil`. This is cosmetic, not a real validation failure — confirmed by checking that `kamal build push` (the command actually used against these two files) runs straight past all config loading/validation and only stops at an unrelated, sandbox-specific missing-`buildx` dependency check. `kamal build push`'s successful progression past config-loading is the actual verification evidence for these two files, not `kamal config`'s output.

**Accessory `service:` overrides keep app code untouched.** `Accessory#service_name` defaults to `"#{config.service}-#{name}"` (e.g. `llm-zoomcamp-project-postgres`), which would resolve as the container's DNS name on the shared `kamal` Docker network. But `rails_app/config/database.yml`'s production block hardcodes `host: postgres`, `EmbeddingClient`/`RerankerClient` default to `http://embedder:8000`, and `grafana/provisioning/datasources/postgres.yml` hardcodes `url: postgres:5432`. Overriding `accessories: { postgres: { service: postgres }, embedder: { service: embedder } }` makes those hostnames resolve exactly as today — zero application code changes. `worker` doesn't need an override; nothing connects to it by hostname.

**Volumes/config mounts map directly onto `docker-compose.yml`'s existing ones**, confirmed via `lib/kamal/configuration/docs/accessory.yml`: `directories:` creates empty, persistent, host-managed directories (matches `postgres_data`/`grafana_data` named volumes) — `directories: [postgres_data:/var/lib/postgresql]`, `[grafana_data:/var/lib/grafana]`. `files:` uploads local repo paths — the docs' own example (`config/certs:/etc/mysql/certs:ro`) implies whole-directory support — matching Grafana's read-only bind mounts: `files: [grafana/provisioning:/etc/grafana/provisioning:ro, grafana/dashboards:/var/lib/grafana/dashboards:ro]`.

**Corrected during implementation: `files:` directory sources don't actually work.** The docs' example is aspirational, not accurate for 2.12.0 (confirmed it's the latest release — not an outdated-gem problem). `Kamal::Cli::Accessory#upload` calls SSHKit's `upload! local, remote` with no options at all; `Kamal::Configuration::Accessory#files` doesn't expand directory entries into per-file mappings either — so a directory `local` path reaches SSHKit's `Net::SCP` upload without `recursive: true`, which raises `Net::SCP::Error: can't upload directories unless :recursive`. Hit this for real on the first `kamal setup` run — every other accessory (`postgres`, `worker`, `embedder`) and `kamal-proxy`/`web` booted successfully; only `grafana`'s `files:` step failed. Fixed by listing each of Grafana's three actual files individually instead of the two parent directories (`grafana/provisioning/dashboards/dashboards.yml`, `grafana/provisioning/datasources/postgres.yml`, `grafana/dashboards/chat-monitoring.json`) — single-file uploads don't hit the same recursive-flag path.

**Also discovered: Grafana's `directories:` mount needs a one-time host-side ownership fix, and always will.** Kamal's `directories:` for accessories is a plain host bind mount (`mkdir -p` on the host, then `--volume host:container`) — unlike local dev's `docker-compose.yml`, which uses a named volume (`grafana_data:/var/lib/grafana`), where Docker/Podman initializes ownership from the image automatically on first use. A raw host directory created by `mkdir -p` (running as root, since Kamal's accessory boot runs over SSH as root) stays root-owned; the official `grafana/grafana` image runs as UID 472, so it can't write to `/var/lib/grafana` and crash-loops on `mkdir: can't create directory '/var/lib/grafana/plugins': Permission denied`. This isn't a one-off fluke — it'll happen again on any fresh VM or fresh `grafana_data` directory (e.g. after a volume wipe), since Kamal has no config-level way to set bind-mount ownership. Fixed for this deploy with `chown -R 472:472` on the host directory followed by `docker restart llm-zoomcamp-project-grafana`; documented as a required one-time step in `tasks.md`'s runbook for any future fresh-volume `kamal setup`, since there's no clean way to automate it through Kamal's own accessory config primitives (`options:` would only change the *container's* user, not fix host directory ownership).

**Discovered during implementation: Grafana needs its own domain, and Cloudflare proxying (enabled mid-session by the user, independent of this change) is incompatible with this VM's setup at the zone level.** Grafana was originally left with no exposed port at all — proxying it through `kamal-proxy` (an accessory `proxy:` block, the same mechanism `web` already uses) needed a real hostname. Tried `grafana.llm-zoomcamp-project.alfonsoalba.com` first — this exposed a real Cloudflare limitation: Cloudflare's free Universal SSL wildcard only covers one subdomain level under the zone apex (`alfonsoalba.com` + `*.alfonsoalba.com`), not a second level, so Cloudflare's edge had no certificate for it at all (confirmed via `curl -v`: the TLS handshake failed at a Cloudflare IP, never reaching the VM). Fixed by using a sibling subdomain instead — `llm-zoomcamp-project-grafana.alfonsoalba.com` (one level deep, covered by the existing wildcard).

That surfaced a second, more serious problem: with Cloudflare proxying active, **both** domains started returning an infinite self-redirect loop (301 to themselves, response headers showing only `cloudflare`, no real backend content) — confirmed the main domain, previously working, had regressed too, not just the new Grafana host. Root cause: Cloudflare's SSL/TLS encryption mode was Flexible (Cloudflare-to-origin over plain HTTP); `kamal-proxy` always redirects HTTP→HTTPS on port 80, and combined with Cloudflare's "Always Use HTTPS," the two redirected each other forever. The correct fix (Full or Full (strict) mode, since `kamal-proxy` already holds a real, valid Let's Encrypt cert) turned out to be infeasible: Cloudflare's SSL/TLS mode is a zone-wide setting on this plan, not per-record, and the user's zone also serves an unrelated production site (`www.alfonsoalba.com`) that a mode change risked breaking.

**Resolution: Cloudflare proxying disabled for both `llm-zoomcamp-project.alfonsoalba.com` and `llm-zoomcamp-project-grafana.alfonsoalba.com`** (DNS-only / grey-cloud, direct A-records to `194.62.98.172`) — reverting to the original design, where `kamal-proxy`'s own Let's Encrypt certs are the sole TLS layer. Confirmed both work cleanly afterward: main domain 302→`/session/new` with real Rails response headers, Grafana 200 with real `/api/health` JSON, both with valid TLS. This means Grafana is reachable directly over the open internet at its own domain, protected only by Grafana's own login — accepted as adequate for a monitoring dashboard in this project's scope, consistent with how local dev already exposes it the same way (no additional reverse-proxy auth layer, unlike the main app which sits behind Rails' `Authentication` concern).

Local registry: `registry: { server: localhost:5555 }` in all three configs. Confirmed via `Configuration::Registry#local?` and `Kamal::Cli::Build#push`'s `forward_local_registry_port_for_remote_builder` — Kamal boots its own registry container on the VM and SSH-tunnels local builds' pushes to it automatically. No external Docker Hub/GHCR account needed.

**Declare `accessories:` in the order `postgres`, `worker`, `embedder`, `grafana` — deliberately, see Decision 4.**

**Corrected during implementation (registry model).** The "local registry" description above was wrong about *where* "local" is. Read `Kamal::Cli::Build#push`/`#setup_local_registry` directly: when `registry.local?`, `kamal build push` *always* runs `docker run --detach ... registry:3` via `run_locally` — i.e. on whichever machine is invoking `kamal`, not on the VM. `forward_local_registry_port_for_remote_builder` only SSH-tunnels *to* that locally-run registry for a remote builder's benefit; it doesn't relocate it. This sandbox has no Docker daemon at all (only `podman`), so the "local registry" approach can't work here regardless of where the build itself executes — confirmed by hitting exactly this wall (`failed to connect to the docker API at unix:///var/run/docker.sock`) after installing `docker`/`buildx` CLI binaries via `mise`.

Resolution: dropped the local-registry approach entirely in favor of **GHCR (`ghcr.io`), with public packages**, plus **`builder.remote: ssh://root@194.62.98.172`** in all three configs so the actual `docker buildx build` execution happens on the VM's own Docker daemon over SSH (confirmed via `Kamal::Commands::Builder::Remote`: it creates a `docker context`/`buildx` builder pointed at the SSH endpoint; `ensure_docker_installed`'s checks are just `docker --version`/`docker buildx version`, which don't need a local daemon). With a non-local registry, `kamal build push` only runs `docker login` locally (`Kamal::Cli::Build#login_to_registry_locally`) — a pure client/HTTP operation against the registry's auth API, no daemon required. This combination needs no Docker daemon anywhere except the VM itself.

Checked actual built image sizes (`web` 991MB, `worker` 1.17GB, `embedder` 1.7GB) against GHCR's free tier: each already exceeds the 500MB/image private-package storage limit, but GHCR storage/bandwidth are free and unlimited for **public** packages — confirmed with the user this is an acceptable trade-off (no secrets are baked into images; only app source/dependencies become visible). `registry.username`/`registry.password` reference `GHCR_USERNAME`/`GHCR_TOKEN` secrets rather than being hardcoded, since the GHCR login username isn't necessarily the same as the `aag-learn` GitHub org/repo namespace the image paths live under.

**Corrected during implementation (token type).** `GHCR_TOKEN` must be a **classic** PAT with `write:packages` scope, not a fine-grained one. Learned the hard way: a fine-grained PAT produced `denied: permission_denied: The token provided does not match expected scopes` on push, and there is in fact no "Packages" permission anywhere in the fine-grained PAT creation UI — confirmed directly against GitHub's own docs (`working-with-the-container-registry`): *"GitHub Packages only supports authentication using a personal access token (classic)."* This isn't a scoping mistake to fix within fine-grained PATs; GHCR simply doesn't support them at all yet.

**Also discovered: Kamal never runs `docker login` locally for a `builder.remote` + non-local-registry combination** (`Kamal::Commands::Builder::Remote#login_to_registry_locally?` hardcodes `false`). Buildx forwards whatever credentials are in the local Docker credential store through the build session regardless of driver, so a one-time local `docker login ghcr.io` (using `GHCR_USERNAME`/`GHCR_TOKEN`) before `kamal build push` is required — this isn't automated by Kamal for this specific combination and has to be documented as an operator step, not something the config alone guarantees.

Image paths gained an explicit `aag-learn/` prefix (`image: aag-learn/llm-zoomcamp-project`, etc.) — `Kamal::Configuration#repository` just joins `[registry.server, image]`, so GHCR's `ghcr.io/<owner>/<name>` convention has to be encoded in `image:` itself, unlike the old local-registry setup where `localhost:5555/<name>` didn't need an owner segment.

Also added an explicit `ssh: { user: root, keys: [~/.ssh/ansible_git] }` block to all three configs, and a matching `Host 194.62.98.172` entry in the operator's `~/.ssh/config` (outside the repo). Necessary because `builder.remote`'s `docker context create ... --docker host=ssh://root@<ip>` is a raw shell-out to the `docker` CLI — it doesn't read Kamal's own `ssh:` config at all, only the ambient SSH resolution (agent/`~/.ssh/config`). The `ssh://root@...` URL in `builder.remote` supplies the user; the `~/.ssh/config` entry supplies the identity file both that raw `docker context` connection and Kamal's own SSHKit-based commands need.

### 2. Thruster on `web` only, HTTP-only (no TLS_DOMAIN) — `kamal-proxy` is the sole TLS terminator

Verified via the installed gem's README and the scratch `rails new`'s real generated files: `Gemfile` gets `gem "kamal", require: false` / `gem "thruster", require: false`; `bin/thrust` is generated via `bundle binstubs thruster` (a normal Bundler command, not something requiring `rails new` — works fine retrofitted onto an existing app); the generated `web`-equivalent `Dockerfile`'s `CMD` is `["./bin/thrust", "bin/rails", "server"]`.

`rails_app/config/puma.rb` already does `port ENV.fetch("PORT", 3000)`, and Puma binds `0.0.0.0` by default — Thruster's automatic `PORT`-forwarding to its child process needs no `puma.rb` changes. The current `web` target's explicit `-b 0.0.0.0` CMD flag becomes unnecessary once Thruster owns the boot.

`worker` is untouched — it has no HTTP surface, Thruster is irrelevant to it.

TLS: Thruster's README documents `TLS_DOMAIN` as opt-in — unset, it runs HTTP-only. Deliberately leave it unset: `kamal-proxy` already owns SSL for the domain, and running two independent TLS terminators would be redundant/conflicting. Thruster listens on its default `HTTP_PORT` (80) internally. Kamal's own `proxy.app_port` also defaults to 80 (confirmed via the generated template's own comment: *"Proxy connects to your container on port 80 by default"*) — no override needed on either side; this alignment is a deliberate Kamal/Thruster ecosystem default, not a coincidence to configure around.

### 3. Health checks go through Thruster (port 80) on both mechanisms

Two independent health checks exist and both should point at the same path:
- **Docker's own `HEALTHCHECK`** (Dockerfile, gates `docker ps` status) — moves from `http://localhost:3000/up` (Puma directly) to `http://localhost:80/up` (through Thruster), so it also verifies Thruster is up and proxying correctly, not just Puma alone.
- **`kamal-proxy`'s own healthcheck** (`proxy: healthcheck: { path, interval, timeout }`, fully independent of Docker's `HEALTHCHECK`) — this is what actually gates the zero-downtime traffic swap during `kamal deploy`. Checked its real default: the prose in `docs/proxy.yml` states *"the proxy will by default hit `/up`"* — the `path: /health` shown in that same file's example block is just an illustrative placeholder value, not the actual default (confirmed in the Ruby source, `Configuration::Proxy#to_h`, that an unset `path` passes through as `nil` to the compiled `kamal-proxy` binary, which applies its own built-in `/up` default). This already matches Rails' built-in `/up` route (already what today's `docker-compose.yml` healthcheck uses) — **no `proxy.healthcheck.path` override needed at all.**

### 4. No Postgres-readiness retry loop in `bin/docker-entrypoint` — rely on Kamal's accessory restart policy (explicit user decision)

Traced Kamal's actual deploy sequence in `Kamal::Cli::Main#deploy` (what `kamal setup` runs): build+push web image → boot `kamal-proxy` → boot **all** accessories, sequentially, in YAML declaration order → stop stale containers → boot the `web` app role → prune.

This means the dangerous race this project already found and fixed once (`rework-startup-dependencies`: `web` and `worker` both concurrently hitting `db:prepare`'s no-advisory-lock fresh-schema path) is now **structurally impossible** — `web` never boots until every accessory, including `worker`, has already gone through its own boot step. That's a stronger guarantee than docker-compose's `depends_on: condition: service_healthy` ever gave in this sandbox (CLAUDE.md documents that condition doesn't reliably enforce under podman-compose here).

A milder residual risk remains: accessories boot sequentially (confirmed via `Kamal::Cli::Accessory#boot`'s `KAMAL.accessory_names.each { |name| boot(name) }` — synchronous per-accessory `docker run -d`) but with no explicit "wait until healthy" gate *between* them. So on a genuinely fresh VM, `worker` could start and attempt `db:prepare` before Postgres has finished its own internal init. Checked `Configuration::Accessory#restart_policy`: accessories default to `--restart unless-stopped`. If `worker` crashes on `PG::ConnectionBad` before Postgres is ready, Docker restarts it automatically, and the retry succeeds moments later.

**Explicit decision: accept the crash-and-restart behavior, do not add retry logic to `bin/docker-entrypoint`.** It's log noise on the very first deploy, not a correctness risk — and `worker`'s db:prepare crashing before writing anything is safe to retry blindly (unlike the original two-concurrent-writers race, there's no partial-write state to worry about here). Adding a readiness-polling loop would be real, permanent added complexity for a problem that already has a real, if inelegant, safety net. `accessories:` declaration order (`postgres` before `worker`) stays deliberate regardless, since it sets the odds of a first-try success.

### 5. A new `.env.production` holds the real deployment secrets — `.env` stays local-only, `.kamal/secrets` sources from `.env.production`

Originally designed as `.kamal/secrets` sourcing straight from the existing root `.env` (Kamal's own generated template's first documented option is reading from the invoking shell's environment: `RAILS_MASTER_KEY=$RAILS_MASTER_KEY`). That doesn't survive contact with the actual requirement, though: `.env` can only hold one value per key, and local dev / the real production deployment need genuinely different values for the same keys — a shared value would mean either identical dev/prod secrets (bad practice: a compromised laptop compromises production) or manually swapping the file's contents before every `kamal deploy` (fragile, defeats the point of a one-command deploy).

Resolution — two files, split by *who reads them*, not by Kamal's own destination mechanism (checked `Kamal::Secrets`: it supports `.kamal/secrets-common`/`.kamal/secrets.<destination>`, but that's for splitting secrets across *multiple Kamal-managed deployment targets* — irrelevant here, there's only one VM):

- **`.env`** (root, existing, gitignored) — unchanged in role: local dev (`bin/dev`) and `docker compose` keep reading it exactly as today. Gains two new keys (see Decision 6): dev-scoped, throwaway `ADMIN_EMAIL`/`ADMIN_PASSWORD`.
- **`.env.production`** (new, gitignored, own `.env.production.example`) — the real deployment values: `RAILS_MASTER_KEY`, `POSTGRES_PASSWORD`, `OPENAI_API_KEY`, `GRAFANA_DB_PASSWORD`, `GRAFANA_ADMIN_PASSWORD`, `ADMIN_EMAIL`, `ADMIN_PASSWORD`. Read *only* by `.kamal/secrets` — never by `docker-compose.yml` or `bin/dev`.

```bash
# .kamal/secrets
set -a; source ../.env.production; set +a
RAILS_MASTER_KEY=$RAILS_MASTER_KEY
POSTGRES_PASSWORD=$POSTGRES_PASSWORD
OPENAI_API_KEY=$OPENAI_API_KEY
GRAFANA_DB_PASSWORD=$GRAFANA_DB_PASSWORD
GRAFANA_ADMIN_PASSWORD=$GRAFANA_ADMIN_PASSWORD
ADMIN_EMAIL=$ADMIN_EMAIL
ADMIN_PASSWORD=$ADMIN_PASSWORD
```

`.gitignore`'s existing `.env` entry is an exact-filename match, not a glob — it does **not** cover `.env.production`, which needs its own line.

**Corrected during implementation — this `.kamal/secrets` design was wrong.** The `set -a; source ../.env.production; set +a` + `KEY=$KEY` pattern above assumed `.kamal/secrets` gets executed as a bash script. It doesn't: `Kamal::Secrets#secrets` calls `::Dotenv.parse(secrets_file, overwrite: true)` (the `dotenv` gem), which parses the file as a dotenv document, not a shell script. A bare `source ...` line isn't valid dotenv syntax and does nothing; `$KEY` interpolation is real (`Dotenv::Substitutions::Variable`) but resolves against the *Ruby process's* `ENV`, not variables a no-op `source` line never actually set. Confirmed directly and severely: `Dotenv.parse(".kamal/secrets")` returned every single key — `RAILS_MASTER_KEY`, `POSTGRES_PASSWORD`, all of them — as an empty string. This would have silently deployed every accessory and the web role with blank secrets; caught only because the very first real use of a `.kamal/secrets` value (the GHCR remote login during `kamal setup`) failed loudly with `cannot perform an interactive login from a non-TTY device` (an empty `-p` value falls through to Docker's interactive prompt, which then fails for lack of a TTY) — everything before that point (`kamal build push` for all three images) never actually exercised `.kamal/secrets` at all, so the bug had no earlier chance to surface.

Fixed by switching to Kamal's other genuinely-supported mechanism: `Kamal::Secrets::Dotenv::InlineCommandSubstitution` really does back-tick-execute `$(...)` per line as a real shell command. Each key now extracts its own value directly: `KEY=$(grep -m1 "^KEY=" .env.production | cut -d "'" -f2)` — relying on every `.env.production` value being single-quoted (see the Decision 6 / token-type correction below and `.env.production.example`) so `cut -d "'" -f2` reliably isolates it. Also caught and fixed a second latent error in the same line: the path must be `.env.production`, not `../.env.production` — Kamal evaluates these `$(...)` commands with the same working directory as wherever `kamal` itself is invoked (the repo root, alongside `config/deploy.yml`), not relative to `.kamal/secrets`' own location inside `.kamal/`. Verified the fix the same way the bug was found — directly via `Dotenv.parse(".kamal/secrets")`, confirming all 9 keys now resolve to non-empty values of the expected length, without ever printing the actual secret values.

### 6. The one admin account is seeded automatically, via the mechanism `db:prepare` already has

Inspected the real Rails 8.1.3.1 authentication generator templates directly (`rails/generators/rails/authentication/templates/`): it scaffolds `User`/`Session`/`Current`, `SessionsController`/`PasswordsController`, and an `Authentication` concern with deny-by-default semantics (`before_action :require_authentication`, `allow_unauthenticated_access` as the opt-out) — no registration/signup controller at all.

Per the explicit "single fixed user, no registration, no password reset" decision: generate the scaffold, then delete `PasswordsController`, `PasswordsMailer` + its views, the password-reset routes, the "forgot password" link in the sign-in view, and their generated tests — following this project's established convention (already applied twice this session, to `MessagesHelper`'s dead partial-dispatch methods and `_error.html.erb`) that unused generated code gets deleted, not left dormant.

Verified `ActiveRecord::Tasks::DatabaseTasks#prepare_all` calls `load_seed` exactly once, only when a database is freshly initialized (`seed = true if database_initialized && db_config.seeds?`). `bin/docker-entrypoint` already runs `bin/rails db:prepare` on every boot, for both `web` and `worker`. So `db/seeds.rb` creates the one admin `User` from `ADMIN_EMAIL`/`ADMIN_PASSWORD`, and it runs automatically the moment the database is first created — no new deploy step, no manual `rails console` on the server, consistent with this project's "no step should require manually running a Rails command" principle. Use `find_or_initialize_by(email_address: ...)` + assign/save (not bare `find_or_create_by!`) so a later `ADMIN_PASSWORD` rotation, followed by a manual `db:seed` re-run, actually updates the password rather than being a no-op against an existing row.

`worker` needs `ADMIN_EMAIL`/`ADMIN_PASSWORD` in its env too (it also runs `db:prepare`/seeds via the shared entrypoint) — same as every other secret both images already share.

**Local dev needs its own `ADMIN_EMAIL`/`ADMIN_PASSWORD` too, in `.env` (not just `.env.production`).** Since `Authentication` has no `allow_unauthenticated_access` exceptions anywhere (Decision, `authentication` capability), `bin/dev` and local `docker compose` also gate every route behind login now — without a local admin user, a developer can't reach their own local instance at all. These are throwaway dev-scoped values, deliberately distinct from `.env.production`'s real ones (see Decision 5).

## Risks / Trade-offs

- **[Risk] 10GB of currently-available disk is tight.** This project's own image sizes: `web` ~700–950MB, `worker` ~900MB–1.1GB, `embedder` ~1.7GB, `postgres` (pgvector) ~450–470MB, `grafana` ~1.4GB — roughly 5GB for one full image set, before Docker's build-cache layers (which can bloat higher mid-build) or accumulated old image generations. → Mitigation: `kamal prune`/`docker system prune` hygiene after each deploy is not optional here; watch disk usage during the first deploy specifically, since that's when build-cache pressure is highest.
- **[Risk] 4GB RAM may be tight under real concurrent load.** Measured `embedder`'s real steady-state footprint directly this session: **~1.04GB RSS** (both models loaded, real traffic served) — before Postgres (~300MB), Grafana (~200MB), `web` (~250MB), `worker` (~200MB), and OS overhead are even counted, that's already close to 2GB with zero headroom for concurrency. → Not mitigated in this change (no swap/resize decision made) — flagged for the user to watch in practice; the VM can be resized if it becomes a real problem, per the user's own stated fallback plan.
- **[Risk] Accessories are not part of Kamal's zero-downtime rolling-deploy machinery** — `kamal deploy` only touches the `web` role; `postgres`/`worker`/`embedder`/`grafana` need explicit `kamal accessory reboot <name>` when their own image/config changes. → Accepted: this is standard Kamal accessory behavior, not something worth working around; `tasks.md`'s deploy runbook documents the explicit accessory-reboot step for `worker`/`embedder` image updates.
- **[Risk] `ADMIN_PASSWORD` rotation requires a manual `db:seed` re-run** (find_or_initialize_by pattern only updates on an explicit reseed, not automatically on every boot) → Accepted as a rare, deliberate operator action, not an automated flow — matches "single fixed user" being a low-frequency, low-automation feature by design.
