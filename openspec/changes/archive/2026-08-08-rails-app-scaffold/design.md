## Context

Ruby (4.0.6) and Rails (8.1.3.1) are already available globally via `mise` on the dev machine, which let several of the decisions below get verified directly (a scratch `rails new` run, inspecting its generated files) rather than assumed — the same discipline used for `pgvector`/`uv`/`mise` findings in earlier changes.

## Goals / Non-Goals

**Goals:**
- `web` and `worker` boot from one codebase, two Docker build targets, matching the architecture in `PLAN.md`.
- `web`'s health is checked via Rails' own built-in endpoint, no custom code.
- `worker` can successfully run `ansible-doc -j <module>`, proven independent of any Ruby code that will call it later.

**Non-Goals:**
- No CSS/JS framework decision — deferred to the Interface change, when there's actually a view to style. `rails new` runs with its own defaults (Propshaft, importmap, Turbo/Stimulus) rather than passing `--css`.

**Reversed after initial completion**: this design originally deferred automatic `db:prepare`-on-boot to the ingestion change, reasoning that this change "has no real migrations to run yet." Revisited once the user raised that project reviewers are explicitly expected *not* to be developers (per `PLAN.md`'s Course rubric context) — requiring a manual `docker compose exec web bin/rails db:prepare` step, even a one-time one, is exactly the kind of step a non-developer reviewer could get stuck on. See decision 9.

## Decisions

**1. `rails new rails_app --database=postgresql --skip-docker --skip-kamal --skip-thruster`, scaffolded inside a `rails_app/` subdirectory, not the repo root.**
- Decided with the user rather than defaulted to: `PLAN.md`'s original layout put the Rails app at the repo root, but `embedder/` already established the pattern of "each component gets its own subdirectory" — extending that to Rails keeps the repo root a short, readable list of components (`embedder/`, `rails_app/`, `openspec/`, `docker-compose.yml`, ...) instead of Rails' many generated top-level directories (`app/`, `config/`, `db/`, `lib/`, `public/`, `storage/`, `tmp/`, `vendor/`, `bin/`, `Gemfile`, ...) mixing in with everything else. Cost: `bin/rails`/`bin/dev` need to run from inside `rails_app/` (or via `-C rails_app`), and the Docker build context becomes `./rails_app` instead of `.` — both minor, one-time adjustments.
- Named `rails_app/`, not `rails/`: verified directly that `rails new rails` fails outright — the app's Ruby module name is always derived from the target directory's basename, and `Rails` collides with the framework's own top-level constant. There's no `rails new` flag to decouple the two. `rails_app` (module name `RailsApp`) was verified to scaffold cleanly with the same flags.
- `--skip-docker`: verified directly (scratch run) that this cleanly omits Rails' own generated `Dockerfile`/`.dockerignore`/`bin/docker-entrypoint` with no partial artifacts left behind. We hand-write our own Dockerfile instead (decision 2) to match this project's existing compose/healthcheck conventions (`postgres`, `embedder`) rather than adapting Rails' Kamal/Thruster-oriented generated one.
- `--skip-kamal`/`--skip-thruster`: this project deploys via `docker-compose`, not Kamal, and doesn't need Thruster's HTTP/2+asset-caching proxy in front of a single-instance capstone app. Skipping avoids generating unused config for tooling we're not using.
- `--database=postgresql`: confirmed this alone adds `gem "pg", "~> 1.1"` to the `Gemfile` and generates a working `config/database.yml` — no manual gem wiring needed.

**2. One multi-stage `rails_app/Dockerfile` with `web` and `worker` build targets, not two separate Dockerfiles.**
- `PLAN.md` originally described two separate files (`Dockerfile`, `Dockerfile.worker`) at the repo root. Diverging from that here: a shared base stage (Ruby install, `libpq-dev`/build tooling, `bundle install`) feeds both a `web` target (just sets `CMD`) and a `worker` target (adds `ansible-core`, sets a different `CMD`) — avoiding duplicating the Ruby/bundler setup across two files that would otherwise need to be kept in sync by hand. `docker-compose.yml`'s `web`/`worker` services both set `build.context: ./rails_app` (matching `embedder`'s `build: ./embedder`) and select the target via `build.target`. Same two distinct final images either way; this just removes a duplication/drift risk.

**3. `web`'s healthcheck hits Rails' built-in `/up` endpoint.**
- Confirmed by inspecting the scratch app's generated `config/routes.rb`: `get "up" => "rails/health#show"` is present by default in a fresh Rails 8 app, returning 200 if the app boots without exception. No custom controller/route needed — same "use what the framework already gives you" approach as the embedder's `/health`.

**4. `worker` gets no Docker/compose healthcheck.**
- Solid Queue's `bin/jobs` process has no HTTP surface to probe, and nothing in this change (or currently planned) needs to `depends_on: worker` with a health condition. Rather than invent a synthetic check (e.g. a PID-file probe) for a signal nothing consumes, `worker`'s container is left with only Docker's basic running/exited state. Revisit if a later change needs to gate something on worker readiness specifically.

**5a. `ansible-core` installed via `uv tool install`, not raw `pip install` or `apt`.**
- Found during implementation, not anticipated at design time: a plain `pip install ansible-core` fails on this Ruby base image's Debian layer with PEP 668's "externally-managed-environment" error, blocking any unqualified system-wide `pip install`. Rather than reach for `pip install --break-system-packages` (works, but explicitly overrides a safety mechanism) or a hand-rolled venv, `uv tool install ansible-core` was used instead — it manages an isolated environment for the tool automatically, sidesteps PEP 668 entirely, and reuses the same `uv` tooling convention already established for `embedder/`. A useful side effect, verified directly: since the Ruby base image has no Python at all, `uv tool install` transparently downloaded its own managed Python interpreter — no separate `apt-get install python3` step needed in the `worker` stage.

**5b. Keep Rails 8's default 4-database topology (primary/queue/cache/cable), confirmed with the user rather than assumed.**
- Verified via the scratch app's generated `config/database.yml`: the `production:` block defines four separate logical databases (`<app>_production`, `_queue`, `_cache`, `_cable`) sharing one Postgres connection (same host/user/password, different `database:` names), and `bin/rails db:prepare` creates and migrates all four in one command — so keeping the default costs nothing operationally over consolidating to one database, just more names to be aware of. `PLAN.md`'s "fits cleanly with the existing Postgres service" refers to the Postgres *server/container*, not a single logical database — this is compatible either way.

**6. `RAILS_ENV=production` inside both containers.**
- This project's containers are the actual (docker-compose-based) way the app runs, not a `bin/dev`-style local-only workflow — `production` is the appropriate Rails environment for that, and it's what activates the 4-database config block from decision 5. Requires `RAILS_MASTER_KEY` to be available at runtime (Rails encrypts `config/credentials.yml.enc` with it); generated by `rails new` into a gitignored `config/master.key`, wired into `.env`/`.env.example` the same way `POSTGRES_PASSWORD` already is — one consistent "secrets live in `.env`, never committed" convention across the project.

**7. `config/database.yml`'s production block is edited to read `ENV["POSTGRES_USER"]`/`ENV["POSTGRES_PASSWORD"]`, not the Rails-generated app-specific env var name.**
- `rails new` defaults to an app-name-derived var (e.g. `LLM_ZOOMCAMP_PROJECT_DATABASE_PASSWORD`). Renaming to the credentials already established by `setup-postgres-compose` keeps exactly one set of Postgres credential env vars for the whole project, rather than two parallel naming schemes for the same underlying secret.

**8. `depends_on: postgres` and `depends_on: embedder` (both `condition: service_healthy`) are wired for `web`/`worker` now, even though no Ruby code calls `embedder` yet.**
- Both are static `docker-compose.yml` relationships, independent of whether application code exists yet to use them. Wiring them now avoids a near-certain later change touching `docker-compose.yml` again just to add a dependency that was already obviously needed.

**9. Automatic database preparation via a dedicated one-shot `prepare_db` service, not an entrypoint script in `web`/`worker`.**
- Alternative considered: an entrypoint script in each of `web`/`worker` that runs `bin/rails db:prepare` before handing off to the real `CMD` (this is what Rails' own `--skip-docker`-omitted generated entrypoint does). Rejected — `docker compose up` starts `web` and `worker` close together, and two processes independently racing to `CREATE DATABASE`/migrate the same four databases at once can produce a transient error on whichever loses the race. `db:prepare` is largely idempotent but concurrent-safety under a literal simultaneous race isn't something to rely on.
- Chosen instead: a `prepare_db` service reusing the `web` build target (same image, no new Dockerfile) with `command: ["bin/rails", "db:prepare"]` and `restart: "no"`, that `depends_on: postgres: condition: service_healthy`. `web` and `worker` both add `depends_on: prepare_db: condition: service_completed_successfully` — Compose only starts them after `prepare_db` exits `0`. No two processes ever touch the databases at the same time; the ordering guarantee comes from Compose itself, not from database-level locking or retry logic in application code.
- Named `prepare_db`, not `migrate` (caught after initial implementation): the service runs `db:prepare`, not `db:migrate` — it also creates the databases from nothing on first run, not just applies schema changes to an already-existing database. `migrate` undersells that and could read as "only handles ongoing migrations," which would be actively misleading once real migrations get added in a later change. `prepare_db` names what the command actually does across its full lifecycle (create-if-missing, then migrate).
- **Verification limitation, found and confirmed directly, not assumed**: this project's containers have been tested throughout via `podman-compose` (1.0.6) in this sandbox, not real `docker compose`. Tested `condition: service_completed_successfully` directly against a minimal two-service compose file: in `podman-compose up` (foreground/attached) it worked correctly, but in `podman-compose up -d` (detached — the mode used everywhere else in this project) it did **not** wait for completion; it translated the condition into Podman's `--requires` flag, which only guarantees *start order*, not *exit-code-gated* sequencing, and started the dependent service while the first was still mid-execution. This is a confirmed gap in `podman-compose` specifically, not in the Compose spec or in real Docker Compose (which implements `service_completed_successfully` correctly) — but it means this project's own local testing cannot fully verify the ordering guarantee the way every other healthcheck-based `depends_on` in this repo has been verified. Documented as an explicit, known verification gap rather than silently claimed as tested.

## Risks / Trade-offs

- **[Risk] `libpq-dev` and build tooling needed in the shared base stage for the `pg` gem's native extension** → standard, well-established Rails+Postgres+Docker requirement; not treated as a special risk, just a necessary `apt-get` line in the base stage.
- **[Trade-off] Multi-stage single Dockerfile (decision 2) is a slightly less obvious read than two separate files** → mitigated by clear stage comments; the duplication a two-file approach would otherwise carry (and the risk of the two files drifting out of sync over time) was judged the worse trade-off.
- **[Trade-off] Four databases (decision 5) means four things `bin/rails db:prepare` must successfully create/migrate before `worker` can start polling** → accepted; this is Rails 8's own idiomatic default and the user confirmed keeping it, not something this change is introducing extra complexity to support.
- **[Risk] `service_completed_successfully` ordering can't be fully verified in this sandbox's `podman-compose`** (decision 9) → Mitigation: the compose config itself is correct per the Compose spec and works as intended under real Docker Compose; verification here is limited to confirming the `prepare_db` service's command succeeds standalone and that `web`/`worker` behave correctly when started *after* it manually. Full automatic-ordering verification should happen the first time this runs under real `docker compose` (e.g. by a peer reviewer, or in CI).

## Migration Plan

- Purely additive: new `rails_app/` directory (Rails app skeleton + `rails_app/Dockerfile`), `docker-compose.yml` gains `web`/`worker`/`prepare_db` services, `mise.toml` gains `ruby`, `.env`/`.env.example` (repo-root, shared) gain `RAILS_MASTER_KEY`, README's Development section extended.
- Rollout: `mise install` (provisions `ruby`), `rails new` scaffold, `docker compose up -d --build`, confirm `prepare_db` exits `0`, `web` reaches `healthy` via `/up`, and `worker`'s logs show Solid Queue polling successfully with no manual `db:prepare` step required.
- Rollback: `docker compose down web worker prepare_db`, remove the added files. `postgres` and `embedder` are untouched by any of this.
