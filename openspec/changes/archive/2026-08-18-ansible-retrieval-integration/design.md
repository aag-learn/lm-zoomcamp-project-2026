## Context

Everything this change needs already exists except the retrieval logic and tool wiring itself — verified directly against the real running stack (71 modules, 1,538 chunks in `rails_app_production`, not the empty local dev DB), not assumed:

- **`Chunk.nearest_neighbors(:embedding, embedding_vector, distance: "cosine")` is a class-level scope** (from the `neighbor` gem's `has_neighbors`), not only the instance method PLAN.md's phrasing could be read either way on. Confirmed directly: querying with a synthetic vector returned real chunks, and a real query embedding for "copy files to a remote host" returned `ansible.builtin.copy::param::src`/`dest` and related chunks as the top results.
- **`Chunk.search`** (existing keyword scope from `ansible-ingestion-pipeline`) returns different, complementary results for the same query (`copy::overview`, `copy::example::6` — chunks the vector search didn't surface) — real evidence that combining the two rankings via RRF will add signal, not just duplicate one list.
- **The `embedder` sidecar's `/rerank` is live and reachable** at `http://embedder:8000/rerank` from `web`/`worker`; a real test call reranked "remote_src: copy from remote" far above "src"/"dest" for a "copy files to a remote host" query — reranking demonstrably changes the ranking, not a no-op.
- **`chat.with_tool(tool, ...)` accepts a pre-built instance, not only a class** — confirmed in the gem source (`tool_instance = tool.is_a?(Class) ? tool.new : tool`). This matters: it means `ChatResponseJob` can instantiate `SearchAnsibleDocs` once per request, hold a reference, and read accumulated retrieval results directly off that instance after `chat.ask` returns — no need to parse persisted tool-call messages back out.
- `RubyLLM::Tool` subclasses use `description`/`param`/`execute` class-level macros (confirmed against the gem source), matching the shape already anticipated in `PLAN.md`.

## Goals / Non-Goals

**Goals:**
- The live chat is genuinely grounded — `SearchAnsibleDocs`/`GetModuleDetails` available as tools, hybrid+reranked retrieval, logged and cited.
- `Retrieval::KeywordSearch`/`VectorSearch`/`HybridSearch` stay independently callable for a later Retrieval Evaluation change.

**Non-Goals:**
- The Retrieval Evaluation rake task (ground truth, 4-strategy hit-rate/MRR comparison) — separate change.
- Query rewriting — separate, not discussed in this change's explore session, still deferred.
- Any UI strategy picker — explicitly decided against; the tool always runs hybrid+rerank.

## Decisions

**`Retrieval::KeywordSearch.call(query)`** — thin wrapper over the existing `Chunk.search(query)`.

**`Retrieval::VectorSearch.call(query)`** — embeds `query` via the existing `EmbeddingClient` (reused as-is, keeping ingestion-time and query-time embeddings on the same model per `PLAN.md`'s original rationale), then calls `Chunk.nearest_neighbors(:embedding, embedding, distance: "cosine")`.

**`Retrieval::HybridSearch.call(query, scope: Chunk.all, limit: 20)`** — runs both of the above (scoped, so module-filtered search stays possible — see below), merges via Reciprocal Rank Fusion (k=60, per `PLAN.md`): a `chunk_id => Σ 1/(k + rank)` hash across both ranked lists, sorted descending, top `limit` returned. The `scope:` parameter is what lets `SearchAnsibleDocs`'s `module_filter:` narrow the search to one module's chunks without needing separate filtered variants of `KeywordSearch`/`VectorSearch`. **Returns an array of `Retrieval::ScoredChunk` (a small `Struct.new(:chunk, :rrf_score)`), not bare `Chunk` records** — the RRF score itself needs to survive past this step so it can end up in `RetrievalLog` alongside the reranker's score (see below), not just be thrown away once it's done its job of producing an order.

**`RerankerClient`** mirrors `EmbeddingClient` closely: Faraday connection, `faraday-retry` middleware (`methods: [:post]`, bounded retries — same lesson learned building `EmbeddingClient`), `POST /rerank`, webmock-based tests. `SearchAnsibleDocs` calls `HybridSearch` for its top ~20 candidates, reranks all of them (pairing each returned score back up with its `ScoredChunk`), keeps the top 5-8 by rerank score for the LLM's context (per `PLAN.md`'s already-specified numbers).

**`SearchAnsibleDocs` tool**: `query:` (required), `module_filter:` (optional fqcn) — when present, scopes `HybridSearch`'s `scope:` to `Chunk.joins(:ansible_module).where(ansible_module: { fqcn: module_filter })` before running search, not filtered after the fact. For each chunk it returns (across possibly multiple calls in one turn), accumulates `{stable_id:, rrf_score:, rerank_score:}` into an in-memory array on the tool instance, for `RetrievalLog` to read afterward.

**`GetModuleDetails` tool**: `fqcn:` (required) — `AnsibleModule.find_by(fqcn: fqcn)&.raw_doc`; returns a clear "module not found" string rather than raising if the LLM passes a bad fqcn (tool `execute` results become LLM-visible text, not exceptions the user sees).

**`RetrievalLog` creation, in `ChatResponseJob`**: instantiate `search_tool = SearchAnsibleDocs.new` before calling `chat.ask`, register both tools via `chat.with_tools(search_tool, GetModuleDetails)`, wrap the call with `Time.current` before/after for `response_time`, read `chat.cost.total` (confirmed available per the installed `ruby_llm` 1.16.0's own upgrade notes) for `cost` immediately after. `input_tokens`/`output_tokens` are read directly off the assistant `Message` itself (`chat.messages.last.input_tokens`/`.output_tokens` — `RubyLLM`'s own `messages` table already has both columns, confirmed back in `chat-interface-scaffolding`) and denormalized onto `RetrievalLog` too, same reasoning as `cost`/`response_time` — avoids a join back to `Message` for later dashboard/eval queries. Build `RetrievalLog` from `search_tool`'s accumulated results: `retrieved_chunks` = `[{stable_id:, rrf_score:, rerank_score:}, ...]` for every chunk returned (not numeric `id`s — see below), `ansible_core_version` = read directly off those same `Chunk` rows (all chunks share one version per ingestion run, so any of them gives the right value), `top_module` = the `ansible_module.fqcn` of the single highest-`rerank_score` chunk from the last `SearchAnsibleDocs` call that turn (the reranker's judgment is the final word on relevance, so it's what decides "top," not the earlier RRF score — simplification: rank-based "top," not frequency — reasonable since `GetModuleDetails` calls don't produce a ranked list to fold in). Only created when at least one `SearchAnsibleDocs` call happened that turn — a reply that didn't need retrieval doesn't get a (misleadingly empty) log row.

**`retrieved_chunks` stores `[{stable_id:, rrf_score:, rerank_score:}, ...]` in `jsonb` — not numeric `Chunk.id`s, and not a flat array.** Corrections from `PLAN.md`'s original phrasing, caught during design review before implementation started:
- *Numeric IDs don't survive re-ingestion.* `ansible-ingestion-pipeline`'s `IngestAnsibleModulesJob` does a full wipe-and-reload weekly — every chunk gets a new numeric `id` every run. A `RetrievalLog` referencing old numeric IDs would silently point at nothing (or a completely different chunk, if IDs were ever reused, though Postgres `bigserial` doesn't do that) after the very next scheduled ingestion. `stable_id` is the identifier already built and verified, back in `ansible-ingestion-pipeline`, specifically to survive re-ingestion — the natural fix is to use it here too. `ansible_core_version` is denormalized alongside it so provenance survives even in the worst case (every referenced `stable_id` later removed from a newer Ansible release, e.g. a deprecated parameter dropped entirely) — considered switching ingestion itself to archive-instead-of-delete chunks instead, which would close that residual gap too, but rejected: it would require a partial unique index on `chunks.stable_id`, `where(archived_at: nil)` scoping added to every retrieval query, and real upsert logic replacing `IngestAnsibleModulesJob`'s deliberately-simple wipe-and-reload — reopening a shipped, already-synced capability's spec text and job logic for a narrow edge case `stable_id`-based storage already degrades gracefully on.
- *Both scores kept, not just one* — `rrf_score` (the hybrid keyword+vector merge rank, before reranking) and `rerank_score` (the reranker's judgment, what actually decided the final order shown to the LLM) are both retained per chunk. Keeping only the reranker's score would lose visibility into whether reranking is actually earning its keep versus the hybrid ranking alone — exactly the kind of signal a later Retrieval Evaluation change would want without having to re-run retrieval from scratch against historical queries. This richer per-chunk shape is what settles `jsonb` vs. a native Postgres array in favor of `jsonb` — a flat array would've been the better fit for a bare ID list, but can't hold `{stable_id, rrf_score, rerank_score}` triples without a redesign.

**Citation rendering must degrade gracefully when a referenced `stable_id` no longer resolves to a `Chunk`.** Use `Chunk.where(stable_id: retrieval_log.retrieved_chunks.pluck("stable_id"))` (a plain `where`, naturally returns fewer rows than IDs requested if some are gone) — never a raising per-ID lookup (`find_by!`, etc.), which would turn a parameter removed in a later Ansible release into a 500 on an old conversation. Missing sources are silently omitted from the citation line, no "N sources unavailable" indicator — a deliberate simplicity call for an edge case unlikely to ever actually occur in this project's lifetime; easy to add later if it does. Same reasoning is why `top_module` is a plain string, not a `belongs_to` FK to `AnsibleModule` — it shouldn't depend on that module still existing either.

**Citations**: render under the assistant message from its `RetrievalLog`, grouped by module — e.g. "Sources: `ansible.builtin.copy` (mode, owner), `ansible.builtin.unarchive` (src)" — resolved from `retrieved_chunks` back through `Chunk`/`ansible_module`, grouping same-module chunks together rather than listing every raw chunk ID. Neither score is shown in the citation UI itself (would be visual clutter for a visitor) — both are stored for future eval/debugging use, not display.

**Testing: real embedding *values*, captured once as fixtures — not a live `embedder` required to run `bin/rails test`.** Initially planned as "run against the real running stack/container," corrected before implementation: `CLAUDE.md` already establishes that tests shouldn't require `embedder` running wherever they run, and CI's `test` job doesn't even bring up an `embedder` service — a retrieval test that needs a live one couldn't run there at all. But a fake placeholder embedding (`Array.new(384, 0.0)`, what the existing association tests use) would make a *ranking* test meaningless — there's no real semantic signal to rank against. The resolution: capture a small set of real embeddings **once** (reusing the exact query/content pairs already verified empirically earlier in this session — "copy files to a remote host" and real `copy`/`uri`/`unarchive` chunk content), store them as a fixture (text → 384-float vector), seed test `Chunk` rows with those captured real vectors, and stub `EmbeddingClient.embed`/`RerankerClient.rerank` (`webmock`, the pattern already established for both clients) to return the matching captured value for each test's specific input. This exercises the real vector math and real ranking logic against real semantic relationships, fast and offline, with no live network call — `Retrieval::KeywordSearch` doesn't even need this (pure Postgres full-text search over plain seeded text). `SearchAnsibleDocs`/`ChatResponseJob` tests use the same captured-fixture-plus-stubbed-client approach underneath their stubbed LLM provider call, so the entire standard test suite never needs a live `embedder`. The genuine live check — real `embedder`, all 1,538 ingested chunks, a real running container — stays exclusively in section 7's verification, as an end-to-end confidence check on top of these, not a replacement for them.

## Risks / Trade-offs

- **`top_module` as "last call's top result" is a simplification** that could pick a less representative module if the assistant made several `SearchAnsibleDocs` calls covering different modules in one turn. → Acceptable for now; revisit only if the dashboard (not built yet) shows this producing misleading "top modules queried" data.
- **Reranking the same ~20 candidates on every `SearchAnsibleDocs` call adds latency** (a real HTTP round-trip to `embedder` per search). → Accepted; the embedder is local/fast (confirmed sub-second in earlier ingestion-time batch tests), and grounding quality matters more than shaving milliseconds off a chat reply.
- **Citations require resolving `retrieved_chunk_ids` back through associations on every render** — not memoized/cached. → Fine at this scale (a handful of chunks per reply); revisit only if it becomes a measurable N+1 problem.
- **A `stable_id` referenced by an old `RetrievalLog` can stop resolving** if the corresponding parameter/example/return is removed in a later Ansible release. → Accepted, handled gracefully (see Decisions) — the citation for that one source just doesn't render; the reply text itself is unaffected, and `ansible_core_version` preserves provenance regardless.
