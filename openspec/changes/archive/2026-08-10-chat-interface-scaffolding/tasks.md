## 7. Live verification

- [x] 7.1 Build and bring up the `web` container with a real `OPENAI_API_KEY` set; send a real message through the browser and confirm a real reply comes back — asked "what is Ansible?" through the real running stack (`web` enqueues → `worker` executes `ChatResponseJob` → real OpenAI call → persisted); got a real, correct answer; `worker`'s logs confirm the job ran (2674ms) and Turbo Stream broadcasts were enqueued. Along the way, discovered `prepare_db` *also* needs `OPENAI_API_KEY` just to boot (RAILS_ENV=production loads all initializers) — corrected in `docker-compose.yml`/proposal.md/design.md, third correction of the same underlying gap-class.
- [x] 7.1b **Fourth correction, found via a real browser after initial curl-based verification passed**: every chat form submission failed with 422 `InvalidAuthenticityToken` in an actual browser. `config/environments/production.rb`'s generated `config.assume_ssl = true`/`config.force_ssl = true` (Rails 8's Kamal-oriented defaults) made Rails treat every request as already-HTTPS without checking, so `request.base_url` reported `https://` over what is actually a plain-HTTP, no-TLS-anywhere `docker-compose` deployment — the browser's real `Origin: http://...` header then failed CSRF's origin match. `curl`-based verification (7.1–7.4) never caught this because `curl` doesn't send an `Origin` header on POST by default. Fixed by commenting out both settings (with a note on when to re-enable — behind a real TLS-terminating proxy, e.g. a future cloud deploy); re-verified with a curl request that explicitly sets `Origin`, confirming both no 422 and no `Secure` flag on the session cookie (which would have broken real browser sessions over HTTP too).
- [x] 7.1c **Fifth correction, found via a real browser**: the chat UI rendered completely unstyled, browser console showing 404s for fingerprinted assets (`application-8b441ae0.css`). `rails_app/Dockerfile` never ran `bin/rails assets:precompile` at all — `public/assets/` (correctly gitignored) never got generated in the image, so no fingerprinted CSS/JS existed to serve. Pre-existing gap from `rails-app-scaffold` (a hand-written Dockerfile, not `rails new`'s generated one, which includes this step by default), invisible until this change's chat UI was the first real page using the asset pipeline — the `/up` health check route never renders a layout. Fixed by adding `ENV RAILS_ENV=production` + `RUN SECRET_KEY_BASE_DUMMY=1 OPENAI_API_KEY=dummy bin/rails assets:precompile` to the `web` build target (dummy values because precompiling boots the full Rails environment, including every initializer that reads a required secret, but never actually uses them). Re-verified: fingerprinted CSS/JS now present in the built image and served with 200, matching exactly what `/chats`' rendered HTML references. Separately noted for the user: this project never actually installed Tailwind (no `tailwindcss-rails`/`cssbundling-rails` gem) despite `PLAN.md`'s original repo-setup notes mentioning `--css=tailwind` — the plain unstyled-but-now-loading CSS is expected, not a second bug; adding Tailwind would be a separate, deliberate scope decision.
