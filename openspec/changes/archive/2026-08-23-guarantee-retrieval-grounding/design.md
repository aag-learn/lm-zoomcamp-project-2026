## Context

See `proposal.md` for the problem. This design was worked out via `/opsx:explore`, with every mechanism below verified directly (gem source, live queries against the real ingested corpus) rather than assumed — see the "Discovered/verified during exploration" subsection for the raw findings this design rests on.

**Current code, for reference:**
- `app/jobs/chat_response_job.rb`: `chat.with_tools(search_tool, GetModuleDetails)` with no `choice:`, no `with_instructions`; `build_retrieval_log(...) if search_tool.retrieved_chunks.any?`.
- `app/services/eval/llm_evaluator.rb#ask_with_tools`: `RubyLLM.chat.with_tools(SearchAnsibleDocs.new, GetModuleDetails).ask(question).content` — same gap.
- `app/tools/search_ansible_docs.rb#execute`: runs `Retrieval::HybridSearch.call` (keyword+vector RRF fusion, no relevance floor — `nearest_neighbors` always returns `limit` chunks) then `RerankerClient.rerank`, and always populates `retrieved_chunks`/`last_call_top_module` whenever any candidate exists, regardless of how weak the rerank score is.
- `grafana/dashboards/chat-monitoring.json`: every panel's `rawSql` reads from `retrieval_logs`, including a "low confidence rate" panel hardcoding `rerank_score < 0.3`.

### Discovered/verified during exploration

- `ruby_llm` 1.16.0 `Chat#with_tools(*, choice:, calls:)` maps `choice:` to OpenAI's `tool_choice` (`providers/openai/tools.rb#build_tool_choice`): `:auto`, `:none`, `:required`, or a specific tool key forces that exact tool. `Chat#update_tool_options`/`forced_tool_choice?`/`reset_tool_choice` (`chat.rb:421-490`) show a forced choice applies to the very next round only, then resets to `:auto` automatically (`chat.rb:339`, `reset_tool_choice if forced_tool_choice?`) — confirmed by reading the gem source, not assumed. This is what makes `choice: :search_ansible_docs` safe to use unconditionally: it can't cause an infinite forced-tool loop, and it doesn't prevent a later round from calling `GetModuleDetails` too.
- `Chat#with_instructions(text)`, when called on an `acts_as_chat`-backed `Chat` (this app's `Chat` model), persists as a `role: :system` `Message` row via `chat_methods.rb#replace_persisted_system_instructions` — calling it idempotently replaces the same row rather than duplicating it on every turn, so it's safe to call on every `ChatResponseJob#perform` invocation of a possibly-multi-turn `Chat`.
- Blanket-forcing `SearchAnsibleDocs` on literally every message (including plain chit-chat) was seriously evaluated. Ruled out for two independent reasons, both confirmed live rather than assumed:
  1. `Retrieval::VectorSearch` has no similarity threshold — `nearest_neighbors(:embedding, embedding, distance: "cosine").limit(limit)` always returns `limit` rows, so a forced search on "Hi, how are you?" still returns 20 candidates and a non-empty rerank result.
  2. A calibration probe against the real ingested corpus (1538 chunks, 71 modules) showed the reranker's score doesn't cleanly separate "genuine but compositional" from "off-topic but lexically similar" queries — see below.
- **Calibration data** (ran via `bin/rails runner` against the real dev database and a locally-running `embedder`, `cross-encoder/ms-marco-MiniLM-L-6-v2`, raw unbounded logits — confirmed via `embedder/main.py`'s `CrossEncoder.predict()` call, no `activation_fn`, so NOT a 0-1 probability):
  - Formulaic ground-truth questions (`data/ground_truth.csv`, e.g. "What data type does the deb parameter expect?"): scored 0.223 to 7.686.
  - Hand-written chit-chat/off-topic ("Hi, how are you?", "What's the weather like today?"): scored -11.3 to -10.8, with one outlier ("What's 2+2?") at -1.555.
  - **This looked like a clean gap — until stress-testing with natural, compositional phrasing broke it**: `PLAN.md`'s own flagship compositional examples scored *lower than the chit-chat outlier*: "create a task to copy a file and set its permissions to 0666" scored -1.046, "write a task to restart a service only when a config file changes" scored -2.444. Meanwhile genuinely off-topic-but-adjacent queries scored in the same range: "how do I write a bash script to copy files" (-1.635), "what's the linux command to change file permissions" (-0.317). No threshold separates these two groups.
- Conclusion: the cross-encoder scores interrogative/factual phrasing far more favorably than imperative/task-writing phrasing, independent of whether the query is genuinely in-scope. A hard content-gate keyed to this score would have suppressed real grounding for this project's own headline use case (writing playbook tasks) — a regression, not a fix.

## Goals / Non-Goals

**Goals:**
- Structurally guarantee `SearchAnsibleDocs` fires on the first tool-call round of every real chat turn and every RAG-condition eval question, so retrieval actually happens rather than depending on the model's own confidence.
- Make Monitoring's `RetrievalLog`-derived panels (volume, latency, cost) reflect all real chat traffic, not only traffic where retrieval happened to fire.
- Keep the fix mechanically simple: no new relevance-scoring infrastructure, no new API calls, no new database columns.

**Non-Goals:**
- No confidence-threshold or relevance-gating logic anywhere in application code — deliberately rejected after the calibration finding above showed no clean, safe cutoff exists for this reranker/corpus/phrasing-style combination. `SearchAnsibleDocs#execute`'s behavior is completely unchanged.
- No recalibration of a "low confidence" signal — the existing Grafana panel using one is removed, not fixed, since building a replacement would reintroduce the threshold problem this design avoids.
- No change to the chat UI's citation rendering (`_citations.html.erb`, `_assistant.html.erb`) — owned by the sibling `hide-tool-orchestration-messages` change, which was updated this session specifically to handle the display consequence of unconditional `RetrievalLog` logging (see Risks below).
- No change to `Retrieval::HybridSearch`, `Retrieval::VectorSearch`, `Retrieval::KeywordSearch`, or `RerankerClient` — the retrieval/reranking pipeline itself is untouched, only when/whether it's invoked and logged.

## Decisions

**Force `choice: :search_ansible_docs`, not `choice: :required`.** `:required` would only guarantee *some* tool call, and the model could still satisfy it by calling `GetModuleDetails` alone (the exact behavior being fixed) if it's confident enough about the fqcn. Naming the specific tool is the only way to guarantee `SearchAnsibleDocs` itself runs.

**No content-gating inside `SearchAnsibleDocs#execute` — always return whatever hybrid+rerank finds, unfiltered, to the LLM.** Given the calibration finding (no clean score threshold), the alternative — suppressing "No results found." for low-scoring searches — risks hiding real grounding for compositional queries that happen to score low. Trusting the LLM to use its own judgment about relevance of the returned chunks is simpler and safer than building gating logic that's been shown empirically not to work cleanly for this corpus.

**`chat.with_instructions(...)` leans on *why*, not just *what*.** The instruction text explains that the ingested corpus is pinned to a specific `ansible_core_version` that may differ from the model's training data — a concrete, falsifiable-sounding reason a confident model is less likely to rationalize past — rather than a bare "always search first" procedural instruction, which is easy for a model that's already confident in its answer to treat as optional. The forced `tool_choice` is what actually *guarantees* the search happens; the instruction's job is to shape what the model does with the (now-guaranteed) results, and to steer multi-round behavior (e.g. calling `GetModuleDetails` after search for the full parameter table) consistent with `PLAN.md`'s original intended flow.

**`RetrievalLog` creation becomes fully unconditional — one row per real assistant exchange, always.** This isn't "compensating" for search sometimes being skipped (that's now structurally prevented); it's a direct correction of a broader problem found while investigating: today, `MonitoringsController` and every panel in `chat-monitoring.json` read exclusively from `retrieval_logs`, so query volume/cost/latency have always been undercounted for any turn that didn't create one — a bigger gap than just "top module is sometimes wrong." Logging unconditionally means Monitoring reflects real usage regardless of what the agent decides to do on any given turn, which is a more robust property than relying on the forced-tool-choice fix holding perfectly forever.

**Remove the Grafana "low confidence rate" panel rather than recalibrate it.** Its existing `rerank_score < 0.3` threshold predates any real calibration and is meaningless on this reranker's raw-logit scale (observed range roughly -11 to +7.7). Recalibrating it properly would mean building exactly the threshold system this design just rejected for the content-gating decision above — for a panel that was already one of `PLAN.md`'s two explicitly-marked "stretch" (non-MVP) charts. Removing it is the lower-risk choice; the "top modules queried" panel (also a stretch chart) is left as-is and will get noisier now that every turn — including off-topic ones — populates a `top_module`, an accepted trade-off rather than something this change solves.

**Both `ChatResponseJob` and `Eval::LlmEvaluator#ask_with_tools` get the same forced `tool_choice`.** Without this, the eval's RAG-vs-no-RAG headline comparison would keep testing "the model's own judgment about whether to search" rather than "answer quality given real retrieval," which is a different (and less interesting) comparison than what `ansible-evaluation`'s spec claims to measure.

## Risks / Trade-offs

- **[Risk] Once `RetrievalLog` is unconditional, `_citations.html.erb`'s current `if assistant.retrieval_log` auto-render would show a "Sources: ..." line under every reply, including plain chit-chat, since it has no relevance check.** → Mitigation: not fixed in this change. The sibling `hide-tool-orchestration-messages` change was updated this session to rework that partial into an opt-in "retrieval details" popup specifically to handle this. The two changes are independent (either can land first; the popup change keeps the existing nil-guard so it degrades gracefully either way) — the user explicitly accepted the interim state (auto-rendered-but-honest citations, and still-visible tool-orchestration bubbles) as acceptable until both land.
- **[Risk] "Top modules queried" panel gets noisier** — every off-topic turn now populates a real-but-meaningless `top_module`. → Accepted, not mitigated: a stretch (non-MVP) chart, and any mitigation would reintroduce the rejected threshold-gating problem.
- **[Risk] Forcing a tool call on every turn adds one embedder round-trip (embed + hybrid search + rerank) to messages that didn't need it (e.g. small talk).** → Accepted: the embedder is a local sidecar, not a paid API — this is a latency cost (likely low hundreds of ms), not a dollar cost, and no calibration data suggested this app sees enough non-Ansible traffic for it to matter at capstone scale.
- **[Risk] `with_instructions` is a soft steer for anything beyond guaranteeing the search call itself** (e.g. whether the model correctly prioritizes the retrieved content over its own memory once both are available) — the forced tool call guarantees retrieval *happens*, not that the model *uses* it correctly. → Not fully mitigated by this change; worth watching via the LLM-eval's RAG-vs-no-RAG accuracy delta after this lands, since that's the existing mechanism for catching this class of regression.

## Migration Plan

No data migration. Purely behavioral: deploy `ChatResponseJob`/`Eval::LlmEvaluator` changes together (both read the same `SearchAnsibleDocs` tool), remove the Grafana panel in the same deploy so the dashboard doesn't briefly show a stale, now-meaningless "low confidence rate" against unconditionally-logged data. No feature flag — this project prefers direct code changes over compatibility shims, and there's no partial/rollout state worth guarding (per-request behavior, no stored state to migrate).
